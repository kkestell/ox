# Workspace instructions from AGENTS.md

Status: implemented and validated on 2026-09-21 with the focused tests and one
isolated headless prompt against a temporary workspace.

## 1. Goal

Let a workspace provide standing model guidance in an `AGENTS.md` file while
keeping the user in control. A user message always takes precedence when it
conflicts with the file.

The first version reads exactly one file: `AGENTS.md` directly inside the
session workspace. It does not search parent or child directories, find a Git
root, read a global file, recognize override or fallback names, or expose
configuration. Those behaviors are separate product decisions and are outside
this change.

Workspace instructions are model context, not conversation. They must affect
every model request in the session without appearing in ACP replay, session
titles, or the transcript.

## 2. Active-session lifetime

Read `AGENTS.md` when a session becomes active in the process and keep that
exact text only in memory:

- ACP `session/new` reads the file for the new active session.
- ACP `session/load` reads the current file if that session is not already
  active in this process. A repeated load reuses its active value.
- Headless `ox run` reads the file for its one new session.

The in-memory value is fixed while that session remains active. Adding,
changing, or deleting `AGENTS.md` takes effect for a new session or when a
saved session is first loaded in a later process. It does not change a session
between prompt runs or repeated loads in the same process.

This lifetime preserves the exact beginning of every model request for an
active session. With unchanged instructions followed by the growing
transcript, each later request retains the earlier request as a cacheable
prefix. Reading the file on every prompt would let a workspace edit invalidate
that prefix from its first message; storing the file in SQLite would make
ephemeral workspace guidance part of durable session state. Do neither.

Create `src/instructions.rs` for the filesystem boundary. Give it one direct
operation that takes the workspace path and returns optional workspace
instructions. Keep activation orchestration in `src/acp.rs`; the session store
must not read or persist workspace instructions.

## 3. File boundary

Use the literal path `<workspace>/AGENTS.md`. Read it as UTF-8 text without
parsing or rewriting Markdown. Whitespace-only content is equivalent to a
missing file and is retained in memory as no instructions.

Bound the file at 32 KiB with a local constant. Check the file without first
allocating an unbounded buffer. If the path exists but is not a readable UTF-8
file, or if its content exceeds the limit, fail session activation with a clear
error naming `AGENTS.md`. Do not truncate the file or silently discard invalid
instructions.

Do not add a watcher, modification-time polling, persistent cache,
configuration option, Markdown parser, or general instruction-file
abstraction. The file is user-controlled workspace input and is intentionally
supplied to the model, but it does not gain operating-system permissions or
bypass any existing tool boundary.

## 4. Process state

Hold workspace instructions in `ServerState` by session ID, alongside the
existing process-local session selections. The map must distinguish an active
session with no `AGENTS.md` from a session that has not loaded instructions
yet, so absence is cached instead of causing a filesystem read on every prompt.

The activation path reads the file before publishing the in-memory entry. A
failed read leaves the session inactive. Deleting a session removes its entry.
Connection shutdown drops all entries normally; no explicit cleanup or
database work is required.

Prompt startup receives the active-session value and copies it into the prompt
run. ACP clients activate a session through `session/new` or `session/load`
before prompting it; treat a prompt for a session with no active entry as an
invalid session operation rather than adding a second, implicit activation
path. Headless execution passes the value it loaded directly and needs no map.

For repeated `session/load`, check the map first and reuse its value. When an
activation does need the file, perform the filesystem operation without
holding the process-state mutex, then publish the result. Session operation
guards keep load and prompt from racing for the same session; different
sessions remain independent.

Do not add a column, table, transcript entry, or other stored representation.
The transcript remains the durable conversation used for ACP replay and model
conversation history. Workspace instructions remain current process context.

## 5. Model request encoding and precedence

Carry the active-session instructions from `PromptRun::open` into every call to
`openrouter::Client::stream_completion`. Change request encoding to prepend one
user-role message when workspace instructions exist, before all messages
projected from the transcript.

Use a fixed wrapper that states the precedence rule plainly:

```text
# Workspace instructions from AGENTS.md

Follow these standing workspace instructions unless they conflict with a user
message. The user's message takes precedence.

<INSTRUCTIONS>
...saved file contents...
</INSTRUCTIONS>
```

The wrapper is part of Ox, not part of the in-memory file content. Keep only the
raw file text in process state so request formatting remains an
OpenRouter-boundary concern. Do not send the instructions as a system message:
workspace guidance must not outrank the user.

Prepend the message on every model request, including requests made after tool
calls. Keep it before the complete transcript each time rather than appending
duplicates to the transcript. Sessions without workspace instructions retain
their current request bodies exactly.

## 6. Failure behavior

An instruction read, encoding, or size error fails the operation activating the
session through its existing error path. For `session/new` and headless startup,
load before `SessionStore::create` so a failure leaves no new session behind.
For the first `session/load` in a process, validate the stored session and
workspace path, load the file, and only then publish active-session state or
replay the transcript. A repeated load uses the existing value and does not
touch the file.

Once an active-session value exists, prompt startup has no instruction-file
failure mode and performs no repeated filesystem check. A prompt for a session
that was not activated fails before saving its user message or starting a model
request.

Do not fall back from an invalid `AGENTS.md` to no instructions. That would make
a session appear usable while silently ignoring guidance the user expected Ox
to follow.

## 7. Tests

Keep the test suite flat where existing tests already own the guarantee:

- Add one table-driven test in `src/instructions.rs` covering a missing file,
  ordinary UTF-8 content, whitespace-only content, invalid UTF-8, and content
  over the limit. This one new test function protects a distinct filesystem
  boundary that does not exist today.
- Extend the existing OpenRouter request-grouping test to assert that the
  wrapped instruction message comes first, the transcript follows unchanged,
  and the wrapper explicitly gives conflicting user messages precedence.
- Extend existing ACP new, load, delete, and prompt tests to cover the
  active-session map without creating separate tests for map mechanics. Assert
  that new and first load capture the current file, prompts and repeated loads
  reuse the captured text after the file changes, delete removes the entry,
  and a prompt for an inactive stored session fails before saving its user
  message.
- Include a failing file case in the existing session-creation coverage and
  assert that no session or active-session entry is created.
- Keep existing no-instructions request assertions to verify that absent
  `AGENTS.md` does not change current message encoding.

After implementation, inspect the complete test diff and report the test
function and test-code delta. The expected function-count delta is `+1`,
justified by the new instruction-file boundary; do not add separate functions
for each input case or repeat persistence and encoding assertions across
layers.

Run focused validation:

```sh
cargo test instructions::tests::
cargo test openrouter::tests::requests_group_messages_and_send_continuation_metadata_once
cargo test acp::tests::
```

Then run one isolated headless prompt with temporary `OX_DATA_DIR` and a
temporary workspace containing an `AGENTS.md` instruction that produces an
observable but harmless response or file choice. Inspect the saved transcript
to confirm that it contains only conversation and no instruction copy.

## 8. Documentation

Update the implemented architecture to identify workspace instructions as
process-local model context captured when a session becomes active. Keep the
transcript described as the single durable conversation, and state that
workspace instructions are neither stored nor replayed.

Add an exact glossary term for **workspace instructions**. Document discovery,
active-session lifetime, precedence, cache behavior, the 32 KiB limit, and
failure behavior in the README. Update the `AGENTS.md` source map for the new
module and the changed responsibilities of `src/acp.rs`, `src/acp/prompt.rs`,
and `src/openrouter.rs`. `src/sessions.rs` does not change.

## 9. Completion criteria

The work is complete when:

1. Both ACP and headless activation capture workspace-root `AGENTS.md` once per
   active session.
2. Every model request for that active session uses the same in-memory content,
   preserving a stable request prefix as the transcript grows.
3. The request places workspace instructions before the transcript and states
   that user messages take precedence.
4. Instructions never appear in SQLite, the transcript, replay, or the session
   title.
5. A later process or session load reads the then-current file, while edits do
   not change an already active session.
6. Missing files preserve current behavior, while invalid files fail session
   activation explicitly.
7. Focused tests and the isolated live check pass, and documentation describes
   the implemented behavior.
