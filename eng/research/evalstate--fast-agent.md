# fast-agent ACP architecture

## Executive summary

- **ACP boundary:** `fast-agent serve --transport acp` (or the `fast-agent-acp` entry point) runs `AgentACPServer` in-process over stdio using Zed's `agent-client-protocol` Python SDK 0.10.1 (`src/fast_agent/acp/server/agent_acp_server.py:860-875` (`run_async`), `pyproject.toml:43`). The server subclasses the SDK's `Agent` and implements `initialize`, `new_session`, `load_session`, `resume_session`, `list_sessions`, `set_session_mode`, `prompt`, and `cancel` (`src/fast_agent/acp/server/agent_acp_server.py:249,607,623,639,691,801,815`).
- **Session model:** The ACP layer owns live session state: `ACPLiveSessionRegistry` maps session ID → dedicated `AgentInstance` plus per-session progress/permission/runtimes (`src/fast_agent/acp/server/live_session_registry.py:15-33`, `src/fast_agent/acp/server/models.py:41-62`). The ACP session ID is generated by and doubles as the durable `SessionManager` directory name (`src/fast_agent/acp/server/agent_acp_server.py:660-661`, `src/fast_agent/session/session_manager.py:1447-1462`, `src/fast_agent/session/identity.py:60-70`).
- **Concurrency:** Different sessions run concurrently (per-session prompt locks, per-session agent instances); prompts for the same session are serialized by a per-session `asyncio.Lock` and queue rather than reject (`src/fast_agent/acp/server/prompt_flow.py:149-174`). Session creation/load holds a global `_session_lock` for the whole setup (`src/fast_agent/acp/server/session_runtime.py:1141`).
- **Durability and replay:** Durable state is JSON files under `<home>/sessions/<session-id>/` — `session.json` snapshot plus rotating `history_<agent>.json` files, written atomically with fsync, guarded by per-session `asyncio.Lock`s and cross-process `filelock` owner leases (`src/fast_agent/session/session_manager.py:452-505,622-637`, `src/fast_agent/session/locking.py:120-177`). `session/load` rehydrates agent histories and replays them to the client as message-chunk updates (`src/fast_agent/acp/server/session_store.py:265-318`).
- **Event flow:** Live updates are sent by directly awaiting `connection.session_update(...)` on the stdio connection: streamed text/reasoning deltas from a per-chunk task, tool-call start/progress/completion inline from the tool-execution path (`src/fast_agent/acp/server/prompt_flow.py:608-666`, `src/fast_agent/acp/tool_progress.py:249-286,832-913`).
- **Notable uncertainty:** None blocking; the main caveats are that `session/load` for an already-live session does not check for an in-flight prompt (the slash-command reload path does), and SDK-internal dispatch semantics were read from the pinned wheel (`agent-client-protocol==0.10.1`), not from this repository.

### ACP surface

Transport is stdio JSON-RPC via `run_agent(self, use_unstable_protocol=True)` (`src/fast_agent/acp/server/agent_acp_server.py:875`); `on_connect` stores the `ACPClient` used for all notifications (`agent_acp_server.py:851-858`). `initialize` echoes the client's protocol version and advertises `load_session`, session `list`/`resume` capabilities, image/embedded-context prompt capabilities, MCP http/sse support, and an auth method (`agent_acp_server.py:249-375`). Handlers are thin delegations: `prompt` → `ACPPromptFlow`, session lifecycle → `ACPServerSessionStore`/`ACPServerSessionRuntime`, slash commands → `ACPServerSlashRuntime` (`agent_acp_server.py:597-813`). The ACP layer is native: it directly drives fast-agent `AgentProtocol` objects; there is no subprocess agent boundary on the agent side. Client-side capabilities are used in the reverse direction: filesystem read/write tools delegate to `connection.read_text_file`/`write_text_file` and shell tools to client terminals when advertised (`src/fast_agent/acp/filesystem_runtime.py:207,309`, `src/fast_agent/acp/terminal_runtime.py:376-401`).

### Runtime and process boundaries

Everything runs in one asyncio event loop. The SDK's dispatcher spawns one asyncio task per incoming request/notification (verified in the pinned wheel: `acp/task/dispatcher.py:76-96`), so a prompt handler runs in its own task — which is exactly what `cancel` targets: `_mark_prompt_active` records `asyncio.current_task()` in `session_tasks[session_id]` (`src/fast_agent/acp/server/prompt_flow.py:239-245`, cancel at `agent_acp_server.py:815-849`). Each `AgentInstance` is built fresh per session (`create_agents_in_dependency_order`) with its own MCP aggregator, i.e., per-session MCP subprocess connections (`src/fast_agent/core/managed_runtime.py:183-215`). A shared `SessionManager` per (sessions-dir, cwd) is reused across that server's sessions with `retain_multiple=True` so `_activate` never drops another live session's owner lease (`agent_acp_server.py:471-488`, `session_manager.py:1527-1535`). File-based `filelock` leases make sessions single-owner across processes (`src/fast_agent/session/locking.py:127-177`); a `session/load` from a second process fails with `-32003` "Session is active" (`session_store.py:573-595`).

## LLM abstraction and integration

### Abstraction

fast-agent uses a **bespoke internal abstraction that calls the vendor SDKs directly**; there is no named third-party LLM/agent framework (Rig, LangChain, etc.). The base class is `FastAgentLLM`, a generic over provider message and response types (`src/fast_agent/llm/fastagent_llm.py:110`). It exposes two abstract seams that each provider implements: `_apply_prompt_provider_specific` for the actual model call (`fastagent_llm.py:1016`) and `_convert_extended_messages_to_provider` for message translation (`fastagent_llm.py:1525`). Providers are enumerated by the internal `Provider` enum (`src/fast_agent/llm/provider_types.py:8`) and bound to internal adapter classes by the `_PROVIDER_CLASS_PATHS` registry (`src/fast_agent/llm/model_factory.py:134-184`), which is loaded lazily with `import_module` (`model_factory.py:1170-1183`). Each adapter instantiates the vendor SDK client itself: `AsyncAnthropic` (`src/fast_agent/llm/provider/anthropic/llm_anthropic.py:751`), `AsyncOpenAI` (`src/fast_agent/llm/provider/openai/llm_openai.py:401-421`), and `google.genai.Client` (`src/fast_agent/llm/provider/google/llm_google_native.py:9,481`). The vendor SDKs are direct dependencies (`pyproject.toml:26-27,34`). The agent tool loop is **inside this repository** (`ToolRunner`, `src/fast_agent/agents/tool_runner.py:133`); no wrapped agent executable or gateway owns the model loop.

### Integration path

1. The ACP adapter invokes the agent's LLM-facing method for a turn: `agent.generate(message, request_params)` or `agent.structured_schema(...)` (`src/fast_agent/acp/server/prompt_flow.py:92-101`). The ACP layer supplies only `RequestParams(system_prompt=...)`; it does not select a model (`src/fast_agent/acp/server/session_runtime.py:516-534`).
2. `Agent.generate` normalizes inputs and calls `generate_impl` (`src/fast_agent/agents/llm_decorator.py:675-733`). Tool-capable agents override `generate_impl` to build a `ToolRunner` and run `until_done` (`src/fast_agent/agents/tool_agent.py:440-493`).
3. Each loop iteration calls `ToolRunner._call_llm` (`src/fast_agent/agents/tool_runner.py:242-249`) → `_tool_runner_llm_step` (`src/fast_agent/agents/tool_agent.py:608-613`) → `generate_impl` → `_generate_with_summary`, which calls `llm.generate(full_history, params, tools)` (`src/fast_agent/agents/llm_decorator.py:912`). `full_history` is the in-memory history plus the new turn, prepared by `_prepare_llm_call` (`llm_decorator.py:968-992`).
4. Provider/model selection happened earlier, when the agent was constructed: `ModelFactory.create_factory(model_string)` parses the spec, resolves the provider, imports the adapter class, and returns a closure that instantiates it (`src/fast_agent/llm/model_factory.py:1113-1166`; parsing at `_resolve_provider_and_model_name`, `model_factory.py:827-853`). Agents attach the resulting LLM via `attach_llm` (`src/fast_agent/agents/llm_decorator.py:414`) from `_finalize_agent` (`src/fast_agent/core/direct_factory.py:306-310,354`).
5. `FastAgentLLM.generate` resolves request params, applies structured-output suppression, then calls `_execute_with_retry(self._apply_prompt_provider_specific, full_history, params, tools)` (`src/fast_agent/llm/fastagent_llm.py:867-962`); the retry wrapper re-raises fatal errors and emits `StreamChunk(event="rollback"/"commit")` around attempts (`fastagent_llm.py:678-724`).
6. In the Anthropic adapter, `_apply_prompt_provider_specific` (`src/fast_agent/llm/provider/anthropic/llm_anthropic.py:3020`) delegates to `_anthropic_completion` (`:2838`), which builds the request via `_prepare_anthropic_completion_request` (`:2733`) and `_build_request_messages_with_history_count`. Messages are converted fresh on every call through `_convert_to_provider_format` → `_convert_extended_messages_to_provider` (`src/fast_agent/llm/fastagent_llm.py:1510-1527`, `llm_anthropic.py:3110-3124`) using `AnthropicConverter.convert_to_anthropic` (`src/fast_agent/llm/provider/anthropic/multipart_converter_anthropic.py:97`). The OpenAI adapter follows the same shape (`_apply_prompt_provider_specific` at `src/fast_agent/llm/provider/openai/llm_openai.py:1549`, conversion at `:1710`).
7. Streaming: `_execute_anthropic_stream` opens `anthropic.beta.messages.stream(**arguments)` (`src/fast_agent/llm/provider/anthropic/llm_anthropic.py:2261-2275`); `_process_stream` (`:1876`) parses raw events and emits `StreamChunk` deltas to registered listeners via `_notify_stream_listeners` (text `_handle_text_delta` at `:1613`, reasoning at `:1569`). The OpenAI path streams `client.chat.completions.create(**request.arguments)` (`src/fast_agent/llm/provider/openai/llm_openai.py:1246,1266`).
8. Tool-call handling: the provider normalizes tool-use blocks into `PromptMessageExtended.tool_calls` (`src/fast_agent/llm/provider/anthropic/llm_anthropic.py:1313-1335,2428,2725-2728`). `ToolRunner.generate_tool_call_response` executes them through the agent's `run_tools` (`src/fast_agent/agents/tool_runner.py:595-645`, `src/fast_agent/agents/tool_agent.py:966-1048`), appends the tool-results user message, and loops; the loop terminates when `stop_reason != TOOL_USE` (`tool_runner.py:282-300`).
9. Conversion back to runtime events: the ACP layer registers a stream listener that maps each `StreamChunk` to `agent_message_chunk`/`agent_thought_chunk` updates and a tool-progress handler for tool calls (`src/fast_agent/acp/server/prompt_flow.py:608-666`; see Event and data flow for the ACP delivery mechanics).

### Provider and tool boundary

- **Provider-specific code** lives under `src/fast_agent/llm/provider/<vendor>/` (`anthropic`, `openai`, `google`, `bedrock`), one adapter class per registry entry (`src/fast_agent/llm/model_factory.py:134-184`). Each adapter owns its request/response normalization by implementing `_apply_prompt_provider_specific` and `_convert_extended_messages_to_provider` (`src/fast_agent/llm/fastagent_llm.py:1016,1525`).
- **Credentials and configuration** are centralized in `ProviderKeyManager`, which resolves a provider key from config file first, then environment variable, then provider-specific fallbacks (`src/fast_agent/llm/provider_key_manager.py:70,194-220,258-307`). Base URL and default headers come from the typed context config (e.g. `context.config.anthropic.base_url`, `src/fast_agent/llm/provider/anthropic/llm_anthropic.py:706-719`).
- **Tool schemas** originate as MCP `Tool` objects from the agent's aggregator (`src/fast_agent/agents/mcp_agent.py:1527`, cached by `ToolRunner._ensure_tools_ready`, `src/fast_agent/agents/tool_runner.py:850-852`) and are converted per provider: Anthropic `BetaToolParam` in `_prepare_tools` (`src/fast_agent/llm/provider/anthropic/llm_anthropic.py:1117-1145`), OpenAI `ChatCompletionToolParam` with `adjust_schema` sanitization (`src/fast_agent/llm/provider/openai/llm_openai.py:1215-1237,1735-1741`). Tool execution itself is provider-independent (`src/fast_agent/agents/tool_agent.py:966`).
- **Multi-provider:** yes. A provider is selected by parsing the model string: an explicit `provider/model` or `provider.model` prefix wins, otherwise `ModelDatabase` / Bedrock pattern matching supplies a default (`src/fast_agent/llm/model_factory.py:784-825,827-853`); the `Provider` enum lists 22 providers including OpenAI-compatible aliases, Bedrock, and Vertex (`src/fast_agent/llm/provider_types.py:8-45`).

### Limits

- The ACP request path does not carry a provider or model: the model is fixed when the agent is constructed from config/card, and the session request params only set `system_prompt` (`src/fast_agent/acp/server/session_runtime.py:516-534`). Model switching is a slash-command/agent-level operation (`set_model`, `src/fast_agent/agents/llm_decorator.py:340-378`), not part of the prompt payload.
- TensorZero is a delegated gateway: the adapter subclasses the OpenAI adapter and posts to a TensorZero OpenAI-compatible endpoint (`src/fast_agent/llm/provider/openai/llm_tensorzero_openai.py:10-56`). Model routing, function resolution, and observability inside TensorZero are outside this repository and are **Not found** here.
- Actual credential values are not in the checkout; only their resolution order and error behavior are (`src/fast_agent/llm/provider_key_manager.py:78-105,225-256`). Checked files: `provider_key_manager.py`, `llm_anthropic.py`, `llm_openai.py`.
- Vendor SDK streaming/transport internals are out of repo; this report traces fast-agent up to its SDK call sites (`anthropic.beta.messages.stream`, `client.chat.completions.create`).

## Session model

### Identity and ownership

A "session" has three coordinated meanings. (1) The ACP session ID, generated on `session/new` by `SessionManager.generate_session_id()` as `<YYMMDDHHMM>-<6 random chars>` (`agent_acp_server.py:660-661`, `session_manager.py:64-73,1447-1462`). (2) The live `ACPSessionState` + `AgentInstance` pair in `ACPLiveSessionRegistry` (one-to-one) (`live_session_registry.py:19-23`). (3) The durable record: the first history save resolves a persisted `Session` whose directory is named exactly after the ACP session ID — `resolve_session_for_save` looks up `manager.get_session(acp_session_id)` and otherwise creates it with `create_session_with_id` (`src/fast_agent/session/identity.py:60-88`, `session_manager.py:818-880`). The ID is stamped in metadata as `acp_session_id` plus `cwd` (`identity.py:109-126`). A session is therefore one-to-one across all three layers, but the durable record exists only after the first prompt (an empty ACP session leaves no directory; `delete_if_empty` prunes such residue, `session_manager.py:613-620`). Within one instance, each named agent keeps its own conversation (`_message_history`) — the ACP "mode" selects the agent per prompt (`prompt_flow.py:285-293`).

### Durable representation

Storage is a directory tree: `<fast-agent home>/sessions/<id>/` where home defaults to the workspace `.fast-agent` (`src/fast_agent/paths.py:98-115`, `agent_acp_server.py:460-469`). Per session: `session.json` — a typed `SessionSnapshot` with metadata (title, cwd, `acp_session_id`), continuation data (active agent, per-agent history files, resolved prompts, git state), and execution status (`src/fast_agent/session/snapshot.py` via `session_manager.py:526-529`); `history_<agent>.json` (plus `..._previous.json` from rotation) holding that agent's serialized `PromptMessageExtended` list, including tool calls/results and reasoning channels (`session_manager.py:463-505`, `src/fast_agent/mcp/prompt_message_extended.py:22-36`). Writes are atomic (temp file, `fsync`, replace) and serialized by a per-session `asyncio.Lock` plus a cross-process checkpoint file lock; mid-turn checkpoints write compact JSON and reuse cached git state (`session_manager.py:349-505,622-637`, `locking.py:158-177`). Stored history is authoritative for both replay and model context: hydration loads it back into `agent.message_history` verbatim (`hydrator.py` via `src/fast_agent/mcp/prompts/prompt_load.py:load_transcript_into_agent`). Deliberately not persisted: ACP chunk-level deltas (only complete messages are stored), slash-command outputs, and tool-call progress notifications.

## Concurrency and isolation

| Scenario | Result | Mechanism and scope | Evidence |
| --- | --- | --- | --- |
| Two prompts in different sessions | `concurrent` | Separate per-session `prompt_lock`s and separate `AgentInstance`s; shared points are the global `_session_lock` (short critical sections), the shared `SessionManager` for the same cwd (per-session `_history_save_lock` + checkpoint lock protect file writes), and the SDK's FIFO sender | `prompt_flow.py:149-174`, `session_manager.py:349-350,373-374`, `session_runtime.py:1141` |
| Two prompts in the same session | `serialized` | `prompt_locks[session_id]` `asyncio.Lock`; the second prompt waits (queued) until the first returns; ACP protocol forbids concurrent prompts per session | `prompt_flow.py:149-174,176-187` |
| Load/resume during an active prompt | Not guarded within the process | `load_session` reuses live state and re-hydrates agents without checking `active_prompts` (the slash-command card-reload path does check and raises); from another process the owner lease blocks the load | `session_store.py:446-479`, `slash_runtime.py:342-350`, `session_store.py:433-441` |
| Delete/close during an active prompt | n/a (no ACP delete) | Shutdown path cancels all prompt tasks before disposing state | `agent_acp_server.py:927-936` |
| Cancellation isolation | Per request/session | `cancel(session_id)` cancels only `session_tasks[session_id]`; no global cancellation state | `agent_acp_server.py:833-849` |

The precise critical sections are: `_session_lock` around registry reads/writes and the whole of session create/load setup (including instance construction and MCP attach — a new session cannot be created while another create/load is in flight, `session_runtime.py:1141-1224`); per-session `prompt_lock` around an entire prompt turn (`prompt_flow.py:167-174`); per-session `_history_save_lock` around file writes (`session_manager.py:373-374`). A subtlety: the shared `SessionManager._current_session` pointer is re-pointed by each save (`session_manager.py:1155-1156`, `identity.py:63-69`); saves are only safe because each `save_current_session` call reassigns and reads `_current_session` synchronously before awaiting, and each save carries its own identity session.

## Event and data flow

### New prompt: ACP client to live response

1. SDK dispatches `session/prompt` as its own task → `AgentACPServer.prompt` → `ACPPromptFlow.prompt` acquires the per-session prompt lock (`agent_acp_server.py:801-813`, `prompt_flow.py:159-174`).
2. Prompt marked active: `active_prompts.add`, `session_tasks[id] = current_task` under `_session_lock` (`prompt_flow.py:239-245`).
3. Session lookup + conversion: instance fetched under `_session_lock`; ACP content blocks converted to MCP content and wrapped as a user `PromptMessageExtended` (`prompt_flow.py:259-283`, `src/fast_agent/acp/content_conversion.py:34-69`).
4. Single-text-block slash commands are handled without the LLM; the response text is sent as one `agent_message_chunk` (`prompt_flow.py:295-325,565-606`).
5. Streaming context: a listener registered on the agent turns each `StreamChunk` into an awaited `session_update` (`update_agent_message_text`, or `update_agent_thought_text` for reasoning), one task per chunk, serialized by `update_lock` (`prompt_flow.py:608-666`).
6. Session-resolved system instruction becomes `RequestParams.system_prompt`; turn-start usage index captured; status-line hook installed (`session_runtime.py:516-534`, `prompt_flow.py:407-420,668-722`).
7. `agent.generate(...)` runs the full tool loop: every LLM response is appended to in-memory history (`src/fast_agent/agents/llm_decorator.py:1044-1045`); tool calls execute through the MCP aggregator whose `tool_execution_handler` is the session's `ACPToolProgressManager`, emitting `tool_call` start/progress/completion updates and `session/request_permission` when needed (`tool_progress.py:249-286,509-663,739-913`, `src/fast_agent/acp/tool_permission_adapter.py:67-127`).
8. Persistence hooks fire inside the turn: after each tool-use response a compact checkpoint is saved (`tool_runner.py:296-298`, `hooks/session_history.py:115-123`); on completion the `after_turn_complete` hook performs a full-fidelity save (`src/fast_agent/core/direct_factory.py:435-451`, `tool_runner.py:311-319`).
9. Finalization: streaming tasks gathered; if no assistant text was streamed the complete response text is sent as one final update; status-line usage metadata attached via `field_meta`; `PromptResponse(stop_reason=..., user_message_id=...)` returned (`prompt_flow.py:421-450,724-798,385-389`; stop mapping at `src/fast_agent/acp/server/common.py:42-73`).

### Durable history to ACP client

1. `session/load` resolves the request cwd, searches the workspace store then the app store, and skips entries whose persisted `cwd` mismatches (`session_store.py:381-441`).
2. `SessionManager.load_session` acquires the cross-process owner lease (`SessionBusyError` → `-32003`); a fresh `AgentInstance` is created and the store attached (`session_store.py:433-459`, `session_manager.py:1054-1085`, `session_runtime.py:961-966`).
3. `SessionHydrator` restores each agent's history file into `agent.message_history`, the active agent, usage, and resolved prompts (`session_store.py:139-180`, `hydrator.py:154-180`).
4. Replay: a `session_info_update` (title/updated-at) is sent, then `build_history_updates` converts every stored user/assistant message's content blocks into `user_message_chunk`/`agent_message_chunk` updates, sent sequentially (`session_store.py:242-318`). Reasoning channels and tool-call/result parts are not replayed — only `message.content` blocks of user/assistant roles are mapped (`session_store.py:251-261`). Corroborated by `tests/integration/acp/test_acp_sessions.py:571-679`.
5. `session/resume` is a thin alias over `load_session` for the unstable method (`session_store.py:489-513`).

| --- | --- | --- | --- | --- | --- |

| Assistant text | `StreamChunk` deltas → assistant message | `agent_message_chunk` per delta (task per chunk); full text as final update only if nothing streamed | assistant `PromptMessageExtended` in history | turn save (or mid-turn checkpoint) | `prompt_flow.py:622-653,750-774`, `llm_decorator.py:1044-1045` |
| Reasoning/thought | `StreamChunk(is_reasoning)` | `agent_thought_chunk` deltas | `channels["reasoning"]` on the assistant message | with the message | `prompt_flow.py:626-627`, `src/fast_agent/llm/provider/anthropic/llm_anthropic.py:2477` |

Persistence happens *before* the prompt response is returned (hooks run inside `agent.generate`), but streamed deltas are delivered *before* the corresponding durable commit — a client can display text that a crash would lose.

### Subsequent-prompt reconstruction

The next prompt needs no special handling: the agent's in-memory `message_history` already contains prior turns, and `use_history` prepends it to the LLM request (`llm_decorator.py:976-992`). After a process restart, `session/load` rehydrates the same list from `history_<agent>.json` (with usage rehydration and prompt restoration), after which prompts behave identically (`hydrator.py:154-180`, `session_store.py:139-180`). Lossy edges: resumed tool-result turns are merged into the following user turn for provider calls (`llm_decorator.py:994-1029`), cancelled turns keep a synthesized error tool result (`tool_runner.py:558-574`), and `session.json`'s continuation (git state, active agent) is advisory.

### Ordering, cancellation, and backpressure

- Text-delta ordering relies on asyncio task-start FIFO plus the `update_lock`; chunk order is preserved in practice, but ordering is an emergent property, not a queue guarantee (Inference from `prompt_flow.py:641-653`).
- Every delta spawns an unbounded task and the SDK's send queue is unbounded (`maxsize=0`); a slow client slows each awaited `session_update`, and pending tasks accumulate until gathered at turn end — many concurrent large streams could queue unboundedly (Inference from `prompt_flow.py:650,734-748`, SDK `acp/task/queue.py:28`).
- Cancellation raises `CancelledError` inside the turn; the loop synthesizes error tool results for in-flight calls, temporarily `uncancel()`s the task to persist reconciled history, then re-cancels; the prompt returns `stop_reason="cancelled"` (`tool_runner.py:302-330,476-495,522-532`, `prompt_flow.py:224-235`, `common.py:22-39`).
- Unknown-session prompts return `PromptResponse(stop_reason=REFUSAL)` rather than a protocol error (`prompt_flow.py:200-207`).
- Save failures are logged warnings and never fail the turn (`hooks/session_history.py:124-129`); provider-key errors surface as ACP `auth_required` (`prompt_flow.py:361-371`).

## Design assessment

### Strengths

- The session ID is a single key across ACP, live registry, and filesystem layout, so load/resume needs no translation table (`identity.py:60-88`, `session_manager.py:818-848`).
- Persistence is embedded in the agent turn via hooks at meaningful boundaries (per tool-loop iteration and turn end), with a cheaper compact format for frequent checkpoints (`tool_runner.py:296-298`, `hooks/session_history.py:112-123`).
- Cross-process safety is explicit: owner leases expose host/pid/surface and produce actionable ACP errors instead of silent divergence (`locking.py:73-156`, `session_store.py:573-595`).
- Cancellation reconciles history deterministically (synthesized interrupted-tool result) so a resumed session is always model-valid (`tool_runner.py:497-574`).

### Tradeoffs and limitations

- Holding the global `_session_lock` for entire session create/load setup serializes expensive work (instance construction, MCP attach) across sessions (`session_runtime.py:1141-1224`).
- `session/load` on an already-live session re-hydrates agents without checking for an active prompt, unlike the reload path which guards (`session_store.py:446-479` vs `slash_runtime.py:342-350`).
- The shared `SessionManager._current_session` pointer is mutated on every save; correctness depends on synchronous reassignment before the first await — fragile under future refactoring (`session_manager.py:1155-1183`).
- Unbounded per-delta tasks and an unbounded SDK send queue give no backpressure policy for slow clients (`prompt_flow.py:650`, SDK `acp/task/queue.py:28`).
- History replay to clients drops reasoning and tool-call structure, so a reloaded transcript is a lossy view of the stored conversation (`session_store.py:251-261`).

### Ideas relevant to Ox

- Mid-turn "checkpoint" saves with a cheaper representation are a good pattern for matching fast-agent's crash resilience without per-token writes (fact: checkpoints fire per tool-loop iteration; tradeoff: extra I/O per tool call versus losing at most one LLM exchange on crash).
- Fast-agent's owner-lease metadata (host/pid/surface) that surfaces in ACP error payloads is worth copying for cross-process session contention UX (fact: `SessionOwner.describe`, `-32003` payload; tradeoff: extra lock files and cleanup paths).
- The queued (wait) semantics for same-session prompts simplify clients but mean a stalled turn blocks subsequent prompts invisibly; Ox would need to decide between queue, reject, and cancel-previous explicitly (fact: `prompt_locks`; judgment: reject/cancel-previous give better feedback).

## Unknowns and conflicts

- SDK dispatch/backpressure semantics were read from the pinned `agent-client-protocol==0.10.1` wheel (`uv.lock:37-45`), not from repository sources; fast-agent behavior was verified only up to its `connection.session_update` calls.
- No ACP handler exists for session deletion/unload; whether clients can ever trigger deletion through ACP was checked in `agent_acp_server.py` handler list — Not found.
- The exact reasoning-replay gap (channels stored but not replayed) is code-implied; no test asserts the absence of thought chunks on load.
- Docs under `docs/` describe ACP usage but were not used as evidence; no disagreement between README claims and implementation was found for the features traced.
