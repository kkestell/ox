# Ox deslop audit

**5 findings warrant action · 3 High · 2 Medium · 0 Low. Nothing fixed.** Three decisions have the highest stakes. Give the new-session form a clear point at which it hands control to the session, prevent a prompt from using an unconfirmed permission mode, and protect ordinary files during socket cleanup. Two smaller corrections also merit action now: give automatic replies the documented prompt attribution, and make the live interrupt test wait for actual output.

**What changed since the last audit.** The comparison is `b9f4a0a` → `6217704`, one commit. The draft now survives until the first send finishes, which introduced a retry with stale settings and extended an existing navigation and text-loss window through Claude startup. The existing-session permission race predates the commit, although its error can now be hidden. Socket cleanup also predates it. The three High findings therefore describe one changed workflow, one older problem with a new consequence, and one older problem discovered on this pass.

## High

### F1. The new-session draft still controls settings and navigation after creation

**Broken guarantees · Changed in 6217704 · Fix the handoff.** The earlier audit found that selecting a draft's prompt could resend it after reconnect. Moving the send out of the view's mount callback addressed that problem. The draft now captures the text and settings, creates the session, sends the prompt, and finally selects the session. Three consequences follow from keeping the draft in control across both requests.

- **Settings.** The draft captures `const { harness, ...settings } = c` before creation, locks the pickers only after `setCreated(id)`, then continues to display `choice().permission_mode`. If the send fails, a second client can configure the parked session, and retry sends only the ID and text under those new settings. The first page can still show the old permission mode. A whitespace-only first prompt reaches this path because creation succeeds before the daemon rejects the send. See `cmd/ox/web/src/SessionView.tsx:139`, `:145`, `:147`, `:175`, `cmd/ox/web/src/ox.tsx:217`, and `internal/server/methods.go:261`.
- **Text.** The editable textarea at `cmd/ox/web/src/SessionView.tsx:160` accepts further typing after line 138 captures the submitted text. On success the keyed view is replaced. The new session has no copy of those edits.
- **Navigation.** The completion at `cmd/ox/web/src/SessionView.tsx:148` calls `props.onSent(id)`. Its caller at `cmd/ox/web/src/App.tsx:51` selects that session even if the user has since chosen another one in the sidebar. That can also discard unsent text in the newly selected view.

At the baseline, successful *creation* already replaced the draft unconditionally. The latest change moved that replacement past process startup and introduced the retained session ID on retry. These consequences share one design decision. Once creation succeeds, use the created session's settings and composer for the pending send or retry. Hand off the submitted text once, preserve subsequent edits, and leave later navigation under the user's control. Keep first-send submission independent of view mounting.

### F2. An existing session can send under the previous permission mode

**Broken guarantees · Pre-existing race, worsened in 6217704 · Fix now.** The settings form calls `setShown(settings)` before awaiting configuration, while the composer's `canSend` checks only sending and execution state (`cmd/ox/web/src/SessionView.tsx:231`, `:233`, `:48`). The two POSTs are independent, and the daemon dispatches each with `go s.handle(reply, line)` at `internal/server/server.go:101`. If Send runs first, Claude starts with the previous mode. If Configure runs first and awaits acknowledgement, Send can fail busy. Session ownership serializes these outcomes correctly on the daemon.

Both controls were already independently enabled at the baseline. The new shared error check, `if (current === latest)` at `cmd/ox/web/src/ox.tsx:118`, can additionally suppress the configuration failure once Send starts. This path needs no partial configuration or database failure of the kind already in the known-issue register. Share the pending configuration with the composer and gate sending until the setting is confirmed or its failure is visible.

### F3. Linux stale-socket cleanup can remove an ordinary file

**Broken guarantees · Pre-existing · Fix now.** When the configured socket path is occupied, the daemon checks for `EADDRINUSE`, dials that path, and on `ECONNREFUSED` calls `os.Remove(path)` before binding again (`cmd/oxd/main.go:89`, `:92`, `:97`, `:100`). A writable ordinary file can yield the same errors on Linux. A mistaken socket path can therefore destroy user data. The cleanup was already present at the baseline. Check the entry with `os.Lstat` and require socket mode before removing it. This is a source conclusion supported by the platform's documented error behavior. [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html#ERRORS)
