## High

### F1. Reconnecting resends a new session's first prompt

High · Broken guarantees · Not fixed · `cmd/ox/web/src/SessionView.tsx:55`

**What's wrong:** A new session's first prompt travels in the selection, and the session view sends it on mount. The selection keeps the prompt after it is sent, so any remount sends it again.

**Consequence:** When the event stream reconnects (for example after restarting `oxd`/`ox` under `make dev`) while a new session is selected and idle, the page sends the first prompt again with no user action, repeating the work and its model cost.

**Evidence:**
- `cmd/ox/web/src/App.tsx:59`: `onCreated={(id, prompt) => select({ kind: "session", id, prompt })}`; `App.tsx:53`: `<SessionView session={session} prompt={prompt()} />` inside a keyed `Match`.
- `SessionView.tsx:55-59`: `onSettled(() => { if (props.prompt) { textarea.value = props.prompt; form.requestSubmit(); } ...`; success only runs `form.reset()` (`:69`) and never clears the selection's prompt.
- `ox.tsx:157-161`: `reload()` sets `s.sessions = {}`, which unmounts the keyed view, then `load()` stores a new session object (`:150-152`), which remounts it with the same `prompt()`.
- `connection.ts:31-34`: every `connection` event calls `onConnect`, which runs `reload()` (`ox.tsx:204`). `send` proceeds when the reloaded state is `idle` or `parked` (`SessionView.tsx:49,65`).

**Proposed fix:** Send the first prompt as part of the create operation in `NewSessionView` and select the session without a prompt.

### F2. Protocol examples use a model ID that oxd rejects

High · Comments and docs vs. code · Not fixed · `docs/protocol.md:143`

**What's wrong:** The `session/create` request example and the `session/get` response example use `"model":"haiku"`, which no configuration offers.

**Consequence:** A client author who copies the request gets `-32602 model "haiku" is not configured`. The document's own configuration examples use `claude-haiku-5-5`.

**Evidence:**
- `docs/protocol.md:143`: `"harness":"claude","model":"haiku","effort":"low","permission_mode":"manual"`; `:184`: `{"model":"haiku",...}`.
- `docs/protocol.md:74,91` and `internal/config/default.json:28,49` use `claude-haiku-5-5`.
- `internal/config/config.go:86`: `return fmt.Errorf("model %q is not configured", model)`, reached from `session/create`'s catalog check.

**Proposed fix:** Use `"model":"claude-haiku-5-5"` in both examples.

### F3. A successful send erases text typed while it was pending

High · Broken guarantees · Not fixed · `cmd/ox/web/src/SessionView.tsx:69`

**What's wrong:** The textarea stays editable while a send is in flight, and the success handler resets the whole form.

**Consequence:** Text typed after pressing Send and before the reply (seconds when a parked session has to start Claude first) is erased without having been sent.

**Evidence:**
- `SessionView.tsx:67`: `const text = String(new FormData(form).get("text"));`
- `SessionView.tsx:69`: `attempt(ox.send(props.session.id, text).then(() => form.reset()))`
- `SessionView.tsx:95`: the textarea has no `disabled` binding; only the Send button is gated (`:98`).
- `docs/protocol.md:153-154`: a parked session starts a process, with a one-minute initialization timeout, before `session/send` answers.

**Proposed fix:** On success, clear the textarea only if its value still equals the sent text.

## Medium

### F4. A queued prompt is invisible in the session's state

Medium · Broken guarantees · Not fixed · `internal/claude/prompt.go:34`

**What's wrong:** After `Send`, the agent is busy (`phase = queued`) but Claude's reported state stays `idle` and no state update is published. The interrupt check and the web client both read that state.

**Consequence:** Between the send's acknowledgment and Claude taking the prompt, the page re-enables Send and the settings (a second send or configure gets `-32002`), offers no Stop button, and `session/interrupt` returns success without writing anything, so the prompt then runs. The interface comment promises that only an idle agent has nothing to stop.

**Evidence:**
- `internal/claude/prompt.go:24-26`: `a.prompt = prompt; a.phase = queued; a.publish(agent.Update{Type: "prompt", ...})`; no state update.
- `internal/claude/prompt.go:34`: `if a.claudeState == "idle" { return nil }`, rather than `a.idle()` (`agent.go:165-167`, which also requires `phase == available`).
- `internal/claude/prompt.go:58-59`: an `idle` report in the `queued` phase is swallowed.
- `internal/agent/agent.go:29-31`: "Interrupt stops the running turn ... an idle agent has nothing to stop."
- `cmd/ox/web/src/SessionView.tsx:49-50,221`: `canSend`, `running` and `configurable` read only `props.session.state`; `ox.tsx:130-153` ignores `session/get`'s `prompt`, and `protocol.ts` omits `message_id`.
- `docs/protocol.md:166-169` tells clients to wait for the prompt's `idle` update; the web client does not track the prompt.
- `internal/server/live_test.go:118` waits for `running` before interrupting, so the queued window is never exercised.

**Proposed fix:** Have Interrupt cancel or reject while `queued`, and have the web client gate Send, settings and Stop on the active prompt as well as the state.

### F5. A tool cut off by process exit shows as running forever

Medium · Broken guarantees · Not fixed · `cmd/ox/web/src/SessionView.tsx:197`

**What's wrong:** A tool entry without a result renders as `running`, with the animated marker. When the process exits mid-tool, no `tool_result` arrives, and nothing marks the tool as ended.

**Consequence:** After Claude crashes or `oxd` shuts down during a tool call, the transcript shows that tool as running indefinitely, including after the session parks and after a page reload, since the unmatched `tool_use` is stored in history.

**Evidence:**
- `SessionView.tsx:197`: `props.tool.result ? (...) : "running"`; `style.css`: `.marker.running { animation: breathe ... }`.
- `ox.tsx:67-70` sets a result only on `tool_result`; `exited` (`:90-91`) appends a separate entry and `parked` (`:78-79`) only sets state.
- `internal/claude/agent.go:180-193`: `exit` publishes `exited` (via `endPrompt`) and `parked`, with no tool results.
- `internal/server/history.go:30` records `tool_use` and `exited`, so a reload rebuilds the same entries.

**Proposed fix:** In `apply`, mark tools still without a result as ended when an `exited` update arrives, and render that status.

### F9. The history test cannot tell a flushed fragment from a pending one

Medium · Hollow tests · Not fixed · `internal/server/history_test.go:40`

**What's wrong:** The test records `"tick"` and `"parked"` and then reads `entries()` from the same `history`, which appends the in-memory pending fragment whether or not it was written.

**Consequence:** A regression that stops writing the last text fragment at park still passes, yet that text would be missing after a daemon restart.

**Evidence:**
- `history_test.go:39-48`: records `text_delta "tick"` and `parked`, then expects `text_delta:tick` from `h.entries()` on the same instance.
- `history.go:68-70`: `if h.pending != nil { updates = append(updates, *h.pending) }`.
- `methods_test.go:120-125` likewise reads the parked session from the same in-memory history.

**Proposed fix:** After `parked`, read entries through a new `history` over the same store.

### F14. The fake harness streams twice after an interrupt and a quick send

Low · Broken guarantees · Not fixed · `internal/fake/fake.go:58`

**What's wrong:** Interrupt leaves a pending tick, which `Handle` discards only while the state is `idle`. A send within the 50 ms tick period sets `running` and starts a second tick chain, and the stale tick continues as well.

**Consequence:** In the dev and test harness, the reply streams through two tick chains at double speed, which can confuse manual testing of interrupts.

**Evidence:** `fake.go:58-60`: `if a.state == "idle" { return // interrupted; a tick was still pending }`; `:108-110`: `Interrupt` calls `finish`; `:96-100`: `Send` sets `running` and calls `a.tick()`.

**Proposed fix:** Stamp ticks with a generation number and drop stale ones.

## Verdict
