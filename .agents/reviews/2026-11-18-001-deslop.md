## High

### F1. A configuration timeout can leave Claude in a permission mode the page does not show

High · Broken guarantees · Not fixed · `internal/claude/configure.go:93`

**What's wrong:** When a control request times out, the agent ends the configuration and becomes available again without knowing whether Claude applied the setting. A late acknowledgement is then ignored, so the agent's record of the process's settings stays at the old value.

**Consequence:** If Claude applies a permission-mode change but acknowledges it after the one-minute timeout, the process runs the new mode while the stored settings and every page show the old one. A later configuration does not repair it: the agent compares against its stale record and skips the permission request, for example when the user changes only effort. The mismatch lasts until the process restarts. This involves permissions, which the Defects policy puts above the fix threshold, and it contradicts the recorded issue's bound ("Until the session's next configuration or process start", `docs/known-issues.md:88`). How often Claude acknowledges this late is unmeasured.

**Evidence:**

- `internal/claude/configure.go:93-96`: `if a.phase == configuring && requestID == a.config.requestID { a.endConfiguration(a.config.fail(errors.New("no control response within one minute"))) }`
- `internal/claude/configure.go:99-103`: `endConfiguration` sets `a.config = nil` and `a.phase = available`.
- `internal/claude/configure.go:76`: `if a.phase != configuring || response.RequestID != a.config.requestID { return }`. A late acknowledgement is dropped, so `a.config.requests[0].apply(&a.settings)` (`:84`) never runs.
- `internal/claude/configure.go:50`: `if settings.PermissionMode != a.settings.PermissionMode {`. Later configurations compare against the stale record.
- Verified by tracing `Configure`, `controlResponse`, `controlTimedOut`, and the server's completion path (`internal/server/methods.go`, `configureSession`). `TestConfigureFailure`'s timeout case (`internal/claude/configure_test.go`) covers the error, not a late acknowledgement followed by another configuration.

**Proposed fix:** On a control-request timeout, stop the process rather than releasing it, so the exit path stores the requested settings for the next process; update the recorded issue's scope.

### F2. The settings form changes effort when the user changes another setting

High · Broken guarantees · Not fixed · `cmd/ox/web/src/SettingsFields.tsx:66`

**What's wrong:** `settingsFrom` rebuilds effort from the configured choices for the form's model, and `changedSettings` then reports that as a change. When a session's model is no longer in the configuration, or its stored effort is no longer one of the model's efforts, changing only the permission mode also sends a new effort.

**Consequence:** If the model was removed from the configuration, the effort field is hidden, the form reads effort as empty, and the request sends `effort: ""`. The Claude agent then sends `effortLevel: null`, resetting Claude to its default effort, and stores the empty effort, without the user seeing any change. If the model is still configured but lost the stored effort, effort silently becomes the model's first. Sessions fall out of the configuration whenever its model list changes, so the trigger is ordinary. This breaks the AGENTS.md rule "A request carries only what the user changed", and invalidates the recorded issue's claim "The web UI sends more than one setting only when a model change also changes effort" (`docs/known-issues.md:80`). It fails silently, which puts it above the fix threshold.

**Evidence:**

- `cmd/ox/web/src/SettingsFields.tsx:20-21`: the effort select renders only `<Show when={efforts().length}>`, and `efforts()` comes from `effortsOf(props.harness, model())` (`:10`, `:55`), which is `[]` for an unconfigured model.
- `cmd/ox/web/src/SettingsFields.tsx:63`: `const effort = String(form.get("effort") ?? "");`
- `cmd/ox/web/src/SettingsFields.tsx:66`: `effort: efforts.some((e) => e.id === effort) ? effort : (efforts[0]?.id ?? ""),`
- `cmd/ox/web/src/SessionView.tsx:179-181`: `settingsFrom(...)`, then `changedSettings(shown(), settings)`, then `configure(settings, changes)`.
- `internal/claude/configure.go:46`, `:108-110`: an empty effort becomes `effortLevel: null`.
- Verified by tracing the form, `changedSettings`, `configureSession`'s merge, and `Configure`.

**Proposed fix:** `settingsFrom` keeps the shown effort unless the user changed the model; then correct the recorded issue's claim.

## Medium

### F4. A failed event stream leaves the page stale with no error

Medium · Broken guarantees · Not fixed · `cmd/ox/web/src/connection.ts:39`

**What's wrong:** When the event stream fails, the connection only clears its ID and rejects pending calls; nothing reaches the page's error display. If `ox` answers the reconnect with an error status, as it does while `oxd` is down, EventSource stops reconnecting.

**Consequence:** If `oxd` stops while a page is open, the page keeps showing the old state, sessions marked running included, with no error until the next action fails with "Not connected to ox". `make dev` now stops `oxd` on the first data race, so a race shows up in the browser this way. It fails silently, which puts it above the fix threshold.

**Evidence:**

- `cmd/ox/web/src/connection.ts:39-42`: `source.onerror = () => { connection = undefined; failPending(new Error("Lost the connection to ox")); };`. No handler reports the error to the page.
- `cmd/ox/main.go:63-66`: `/events` answers `http.StatusBadGateway` when it cannot dial `oxd`.
- `cmd/ox/web/src/ox.tsx:183`: the page passes only `onConnect` and `onNotification`.
- `docs/architecture.md:139` ("Each new connection clears the store and loads it again") assumes a reconnect that does not happen after an error status. The EventSource behavior is from its specification, not reproduced here.

**Proposed fix:** Report stream errors to the page, and clear the error on reconnect.

### F5. The docs disagree about which permission mode a resumed process uses

Medium · Comments and docs vs. code · Not fixed · `docs/claude-code.md:33`

**What's wrong:** Ox's reference on Claude Code says the permission mode is restored from the transcript on resume, while the protocol promises that settings stored on a parked session apply to its next process. Ox passes `--permission-mode` on every launch, but no doc says whether the flag wins over the restored mode, and no test checks it.

**Consequence:** If the transcript's mode wins, a permission mode changed while a session is parked shows as changed while the resumed Claude runs the old one. That would be a permissions mismatch above the fix threshold. Which behavior holds is unverified.

**Evidence:**

- `docs/claude-code.md:33`: "Per-process flags (…, model, effort) must be passed again on every resume. The permission mode is restored from the transcript."
- `docs/protocol.md:225`: "A parked session stores the settings and applies them when its next process starts."
- `internal/claude/claude.go:41`: `args = append(args, "--model="+settings.Model, "--permission-mode="+settings.PermissionMode)`, including on `--resume`.
- `TestLive` (`internal/server/live_test.go`) never changes the mode of a parked session and resumes it.

**Proposed fix:** Establish live which mode a resumed process runs, then correct the wrong doc, or the launch if the transcript wins.

### F6. A failed approval answer leaves a stale approval on every page

Medium · Broken guarantees · Not fixed · `internal/claude/approval.go:41`

**What's wrong:** `Approve` removes the approval before writing the answer to Claude. If the write fails, it returns the error without publishing `approval_answered` or `approval_cancelled`, and the later exit cannot withdraw the approval because it is no longer pending.

**Consequence:** If Claude's input is closed when an approval is answered, every page keeps an approval that no longer exists. Answering it again returns "approval request is no longer pending", and `parked` does not clear it, so it stays until the page reloads. This breaks the protocol's "When Claude cancels a request, becomes idle, or exits, Ox withdraws unanswered approvals" (`docs/protocol.md:347`). The failure is visible and costs only Ox's own view, so it is below the fix threshold.

**Evidence:**

- `internal/claude/approval.go:41-45`: `delete(a.approvals, requestID)`, then `if err := a.input.Respond(requestID, response); err != nil { return err }`.
- `internal/claude/approval.go:58-62`: `withdrawApprovals` cancels only the IDs still in `a.approvals`.
- `cmd/ox/web/src/ox.tsx:69-71`: `case "parked": session.state = "parked";` leaves `session.approvals` untouched.
- Both reviewers reported it independently. `internal/claude/approval_test.go` does not cover a failed write.

**Proposed fix:** Record in `docs/known-issues.md`.

### F7. The live failed-turn check can pass without a failed turn

Medium · Hollow tests · Not fixed · `internal/server/live_test.go:164`

**What's wrong:** The scheduling check requires only that Haiku called `CronCreate` and `Bash`. It never confirms that Bash asked for approval, that the denial with `interrupt: true` was sent, or that the turn ended without a Stop hook.

**Consequence:** If Bash runs without asking, the turn completes normally, the Stop hook reports the cron, and the session stays running. The test then passes while checking a second completed-turn case, leaving the failed-turn guarantee untested. An earlier ad hoc run with `echo done` behaved this way.

**Evidence:**

- `internal/server/live_test.go:155-160`: `denyBash` returns the interrupting denial, but nothing records that it ran.
- `internal/server/live_test.go:164-165`: `if !slices.Contains(tools, "CronCreate") || !slices.Contains(tools, "Bash") {`
- `internal/server/live_test.go:174-175`: `if parked(failed) { t.Error("a failed turn that created a cron let its session park") }`
- `internal/server/live_test.go:74`: `turn` returns at the first `idle` regardless of how the turn ended.

**Proposed fix:** Fail the check unless the interrupting denial was sent.

### F9. A configuration that omits a list breaks the web UI

Medium · Broken guarantees · Not fixed · `cmd/ox/web/src/SettingsFields.tsx:83`

**What's wrong:** `config.Load` accepts a harness or model that omits `models`, `modes`, or `efforts`, and `harness/list` then sends `null`. The UI types those as arrays and indexes them without checking.

**Consequence:** A non-default harness whose first model omits `efforts` breaks the new-session form when that harness is chosen, and a harness that omits `models` or `modes` also breaks its sessions' views. The docs describe a model without effort levels as valid, which invites omitting the key. The current local configuration lists `efforts` for every model, so it does not trigger this. It fails visibly, so it is below the fix threshold.

**Evidence:**

- `internal/config/config.go:36-37`, `:45`: `Models []Model`, `Modes []Option`, `Efforts []Option`. Omitted keys decode to nil and marshal as `null`.
- `cmd/ox/web/src/protocol.ts:6-7`: `efforts: Option[]`, `models: Model[]`, `modes: Option[]`.
- `cmd/ox/web/src/SettingsFields.tsx:83`: `model?.efforts[0]?.id` and `harness.modes[0]?.id` throw on `null`. `:38` (`props.options.some(...)`) throws when `options` is a null `models` or `modes`. `effortsOf` (`:55`) tolerates a null `efforts` through `?? []`.

**Proposed fix:** Record in `docs/known-issues.md`.
