## F1. Deleting state lives outside the server lock

High · Plan

Tracked in [#187](https://github.com/kkestell/ox/issues/187).

Whether a session is being deleted is stored in `session.deleting`, owned only
by the session's goroutine, while `readyLocked` and `reportersLocked` decide
report eligibility solely from facts guarded by `Server.mu` (`closed`,
`archived`, `state`, and `reporting`). Because `Server.mu` readers cannot see
that a session is being deleted, `destroy` works around the gap in two ways: it
clears `sess.reporting = nil` under `Server.mu` before `removeWorktree` runs,
and it calls `sess.stop()` before setting `sess.deleting`.

Before agent-started top-level sessions (#175), a reporting recipient always
had child sessions (which refused deletion before `destroy` reached `stop`),
and a reporter was always a child (which has no worktree, so deletion did not
fail after `stop`). Top-level sessions started with `create_top_level_session`
report to their creator without blocking deletion, and both creator and started
session can own worktrees whose deletion fails in normal use when uncommitted
changes are present.

The wrong states this permits in normal use:

- **Refused creator delete drops every waiting report.** When a creator with a
  dirty worktree is running while a started session finishes and holds a
  report, `session/destroy` calls `sess.stop()` before setting `sess.deleting`.
  `stop()` publishes `UpdateParked`, which calls `familyChangedLocked(sess)`.
  `readyLocked(sess)` sees a parked, unarchived session and schedules
  `deliverReports`. `deliverReports` runs on the creator's goroutine while
  `sess.deleting != nil`: `takeReports` drains and wipes `r.reporting.reports`
  under `Server.mu`, and `acceptMessage` -> `start()` refuses with
  `errDeleting`, logging `deliver reports: session is being deleted`.
  `removeWorktree` then fails with `worktree has uncommitted changes`, leaving
  the creator parked and listed with its started session's report permanently
  lost. The same loss occurs if a reporter finishes while `removeWorktree` is
  running on the creator.
- **Refused started-session delete drops its own held report.** When a started
  session with a dirty worktree finishes its turn while a sibling reporter is
  still running (so its report is waiting in `sess.reporting.reports`),
  `session/destroy` sets `sess.reporting = nil` before `removeWorktree` fails.
  `finishDelete` then replaces `sess.reporting` with a blank `newReporting()`,
  permanently losing the completed turn's report even though the session was
  never deleted.

### Places

- `internal/server/session.go:61` — `reporting` is mutated between `nil` and
  `newReporting()` under `Server.mu` to stand in for deleting state.
- `internal/server/session.go:74` — `deleting` is owned by the session
  goroutine alone, invisible to `Server.mu` readers.
- `internal/server/session.go:469` — `start` refuses with `errDeleting` only
  after `deliverReports` has already drained reporters' queues.
- `internal/server/session.go:547` — `destroy` clears `sess.reporting = nil`
  before `removeWorktree`, discarding held reports before deletion succeeds.
- `internal/server/session.go:553` — `destroy` calls `sess.stop()` before
  setting `sess.deleting`, emitting `UpdateParked` and triggering
  `familyChangedLocked(sess)`.
- `internal/server/session.go:577` — `finishDelete` clears `sess.deleting` and
  on failure allocates a fresh `newReporting()`, losing prior reports and never
  re-evaluating `familyChangedLocked`.
- `internal/server/session.go:741` — `readyLocked` reads `closed`, `archived`,
  `state`, and `reportersLocked` without checking whether the recipient or a
  reporter is deleting.
- `internal/server/session.go:770` — `deliverReports` / `takeReports` drains
  `r.reporting.reports` under `Server.mu` before `acceptMessage` discovers
  `sess.deleting != nil`.
- `internal/server/mcp.go:502` — `checkChildLocked` reads `parent.deleting`
  under `Server.mu` only by relying on running on the parent's goroutine.

### Defects

- The November 25 structural audit F1 (#127) unified report delivery under
  `Server.mu` (`readyLocked` and `familyChangedLocked`), leaving `deleting`
  outside `Server.mu` and guarding child deletion by clearing `sess.reporting`
  before `sess.stop()`.
- #175 extended reporting to top-level worktree sessions, making failed
  deletions after `sess.stop()` reachable in normal use.

### Evidence

Reproduced both cases with a race-enabled Go probe in `internal/server`
(removed after the run):

1. Creator in a dirty worktree running `wait 60000` starts a top-level session
   whose turn finishes (`idle`). Calling `session/destroy` on the creator
   returns `worktree has uncommitted changes`; the log records
   `deliver reports: session is being deleted`, and the creator remains
   `parked` and listed with `0` reports received.
2. Creator starts two worktree sessions (`w1`, `w2`). While `w2` runs
   `wait 600`, `w1` finishes `done fast`, its worktree is dirtied, and
   `session/destroy` on `w1` returns `worktree has uncommitted changes`. When
   `w2` finishes, the creator receives only `w2`'s report; `w1`'s report is
   gone.

### Replacement

Guard `deleting` under `Server.mu` beside `archived` and `state`, set it before
`sess.stop()` in `destroy`, and clear it under `Server.mu` in `finishDelete`
when deletion fails. Keep `sess.reporting` immutable for the lifetime of any
session with `reportsTo() != ""`: `report` records nothing while `sess.deleting
!= nil`, `readyLocked` returns false when the recipient is deleting and treats
a deleting reporter as not running (or omits its reports only once it leaves
`s.sessions`), and `finishDelete` calls `familyChangedLocked` on failure (for
`sess` and its recipient) and on success (for the recipient after removing
`sess` from `s.sessions`).

This removes the eager `sess.reporting = nil` / `newReporting()` shuffle in
`destroy` and `finishDelete`, removes the goroutine-only caveat on
`checkChildLocked`, and makes it impossible for a failed deletion to drop
either the session's own reports or reports addressed to it. The change is
confined to `internal/server/session.go` and its tests and preserves all
documented requirements.

## F2. Agent-started top-level sessions publish before accepting their first message

Medium · Plan

Tracked in [#188](https://github.com/kkestell/ox/issues/188).

Ox creates agent-started sessions in two opposite orders. `create_session`
(`addChild`, fixed by #167 for sweep F9 / #147) keeps the new session outside
`s.sessions` until `AddSession`, `sess.start()`, and `sess.acceptMessage()` all
succeed, rolling back on any failure so nothing is stored or broadcast.
`create_top_level_session` (#175) instead calls `createTopLevel`, which stores
the row, broadcasts `session/created` as `parked`, and starts `sess.run()`, and
only then looks `sess` back up in `s.sessions` and posts `acceptMessage`.

In addition, `createTopLevelSession` notes at `mcp.go:574` that a caller being
deleted is "refused by the creation's own checks", but neither `startedRecord`
nor `createTopLevel` checks `caller.deleting` or `caller.archived` (unlike
`checkChildLocked` for `create_session`).

The wrong states this permits in normal use:

- **A failed launch strands an empty session, worktree, and branch.** The
  built-in configuration offers Ur alongside Claude, and `oxd` starts normally
  without `OPENROUTER_API_KEY`. When a Claude session calls
  `create_top_level_session` with `harness: "ur"` (or any harness whose binary
  fails to launch or whose first write fails), `createTopLevel` creates a real
  git worktree and `ox/<id>` branch, inserts the session into SQLite, and
  broadcasts `session/created`, before `acceptMessage` fails with
  `OPENROUTER_API_KEY is not set`. The tool returns
  `session <id> was created, but refused its first message: ...`, leaving an
  empty parked session in the sidebar and a worktree and branch on disk for the
  user to clean up.
- **A brief parked window and shutdown-error mismatch.** Between
  `createTopLevel` returning and `acceptMessage` running, clients see the
  started session as `parked`, and another request can race to archive or
  delete it before its first message arrives (which then reports
  `errShuttingDown` if `s.sessions[record.ID]` is nil).

The plan for #175 (`agents/plans/2026-11-27-agent-top-level-sessions.md:60–67`)
chose publish-first deliberately:

> "Publishing first lets both callers share `createTopLevel`, which publishes
> under `s.mu` where no harness may launch. A first message the new session
> refuses (its harness cannot launch) leaves the session listed and parked; the
> tool's error names it: `session <id> was created, but refused its first
> message: <err>`."

Both parts of that rationale can be answered without publishing first:
`createTopLevel` already releases `s.mu` while creating a worktree and tracks
in-flight creations with `s.creations`, and `session.update` already gates
broadcasts on `s.sessions[sess.id] == sess`. Running an optional preparation
step (store, `sess.start()`, `sess.acceptMessage()`) off `s.mu` before
`publishLocked`, and rolling back the agent, stored row, and worktree on
failure or shutdown, keeps one shared creation path without launching under
`s.mu`.

### Places

- `internal/server/mcp.go:449` — `addChild` owns an unpublished child until its
  first message is accepted, rolling back on failure.
- `internal/server/mcp.go:574` — `createTopLevelSession` comment assumes
  creation checks reject a deleting caller, though none check `caller.deleting`
  or `caller.archived`.
- `internal/server/mcp.go:605` — `createTopLevelSession` publishes via
  `createTopLevel`, looks `sess` back up under `s.mu`, posts `acceptMessage`,
  and formats the partial-failure error.
- `internal/server/mcp.go:637` — `startedRecord` resolves settings without
  checking caller `archived` or `deleting`.
- `internal/server/methods.go:419` — `createTopLevel` always calls `addSession`
  (which publishes and starts `sess.run()`) before returning.
- `internal/server/methods.go:516` — `addSession` couples storing, publishing,
  and starting `sess.run()` inside one `s.mu` critical section.

### Defects

- Sweep F9 (#147, fixed in #167) fixed the same publish-before-accept defect
  for `create_session`.
- PR #175 review F3 noted the `sess == nil` -> `errShuttingDown` mismatch
  created by looking up the session again after `createTopLevel` returned.

### Evidence

Reproduced with a race-enabled Go probe in `internal/server` (removed after the
run) with `OPENROUTER_API_KEY` unset and both `fake` and `ur` configured:

- `create_session` with `harness: "ur"` returned `refused=true`,
  `"OPENROUTER_API_KEY is not set"`, and left 0 new sessions in
  `workspace/list`.
- `create_top_level_session` with `harness: "ur"` and `worktree: true` returned
  `refused=true`, `"session <id> was created, but refused its first message:
  OPENROUTER_API_KEY is not set"`, and left a parked session in
  `workspace/list`, a registered worktree in git, and an `ox/<id>` branch in
  the repository.

### Replacement

Let `createTopLevel` accept an optional pre-publish first message (or setup
callback) that runs off `s.mu` under `s.creations`, after `addWorktree` (when
requested) and `AddSession`: call `sess.start()` and `sess.acceptMessage()`
while the caller still owns `sess`, then acquire `s.mu` to check `s.closed`,
workspace membership, and caller state before `publishLocked` and
`go sess.run()`. On any error or shutdown, call `sess.agent.Stop()`,
`deleteUnpublished(sess)`, and `discardWorktree` (if a worktree was created).

This removes the post-publish `s.sessions[record.ID]` lookup, the
`sess == nil` -> `errShuttingDown` fallback, the partial-failure error format,
and the stranded session/worktree state, while keeping one shared top-level
creation path. Because a failed launch in `create_top_level_session` will no
longer leave a listed session or worktree or return the partial-failure message
string, `/ox-plan` should confirm that behavior change with the user.

## F3. Web client expects Claude prefix on Ox tool names

Medium · Plan

Tracked in [#189](https://github.com/kkestell/ox/issues/189).

Ox's six MCP tools (`list_sessions`, `list_models`, `read_session`,
`send_message`, `create_session`, `create_top_level_session`) have one
definition in `internal/server/mcp.go`, but arrive in `tool_use` updates under
two names: Claude Code prefixes them `mcp__ox__<name>` because
`internal/claude/claude.go` registers the server as `"ox"`, while Ur emits the
bare MCP tool names (`send_message`, `create_session`, etc.) because
`internal/ur/engine/mcp.go` passes `tools/list` names straight to the model and
back in `tool_use`.

`cmd/ox/web/src/toolInput.ts` still assumes every Ox tool arrives with
`OX_PREFIX = "mcp__ox__"`, both when formatting tool labels (`toolLabel`) and
when selecting the summary field (`OX_SUBJECT_FIELD`).

The wrong states this permits in normal use:

- Every Ur call to an Ox tool renders its raw snake_case name (`send_message`,
  `create_session`, `create_top_level_session`, `list_sessions`, `list_models`,
  `read_session`) instead of PascalCase (`SendMessage`, `CreateSession`, etc.).
- Every Ur call to `send_message`, `create_session`, or
  `create_top_level_session` misses `OX_SUBJECT_FIELD` and falls back to the
  first string in the JSON input: `send_message` shows the opaque target
  session ID (`to`) instead of `text`, `create_session` shows the slug `name`
  instead of `title`, and `create_top_level_session` shows `message` instead of
  `title`.

### Places

- `internal/server/mcp.go:140` — defines Ox's six canonical MCP tool names.
- `internal/claude/claude.go:66` — registers the MCP server as `"ox"`, causing
  Claude Code to emit `mcp__ox__<name>`.
- `internal/ur/engine/mcp.go:114` — forwards Ox's MCP tool definitions to Ur's
  model under their bare names.
- `internal/ur/engine/engine.go:582` — reports Ur's tool calls to `oxd` under
  those bare names.
- `cmd/ox/web/src/toolInput.ts:7` — hardcodes `OX_PREFIX = "mcp__ox__"` in
  `toolLabel` (`:11`) and `OX_SUBJECT_FIELD` (`:22`).
- `cmd/ox/web/src/SessionView.tsx:335` — passes raw `props.tool.name` to
  `toolLabel` and `toolSummary`.

### Defects

- #168 (`2026-11-27-ur-ox-tools.md`) gave Ur access to Ox's MCP tools under
  their bare names without updating `toolInput.ts`.
- #175 (`2026-11-27-agent-top-level-sessions.md`) added
  `mcp__ox__create_top_level_session` to `OX_SUBJECT_FIELD` and again missed
  Ur's bare name.

### Evidence

Confirmed directly with `node --experimental-strip-types` importing
`cmd/ox/web/src/toolInput.ts`:

- `mcp__ox__send_message` -> label `"SendMessage"`, summary `"Tests pass"`;
  bare `send_message` -> label `"send_message"`, summary `"4kP9mN2qX8v"`
  (the `to` session ID).
- `mcp__ox__create_session` -> label `"CreateSession"`, summary `"Review: F1"`;
  bare `create_session` -> label `"create_session"`, summary `"review-f1"`
  (the `name` slug).
- `mcp__ox__create_top_level_session` -> label `"CreateTopLevelSession"`,
  summary `"Fix retry loop"`; bare `create_top_level_session` -> label
  `"create_top_level_session"`, summary `"Fix retry"` (the `message` field).
- `mcp__ox__list_sessions` -> label `"ListSessions"`; bare `list_sessions` ->
  label `"list_sessions"`.

### Replacement

Normalize Ox tool names in one helper in `cmd/ox/web/src/toolInput.ts`: strip
an optional `mcp__ox__` prefix and match against the canonical set of Ox tool
names (and a single unprefixed `OX_SUBJECT_FIELD` map), so both Claude's
`mcp__ox__<name>` and Ur's `<name>` format identically while non-Ox tools (such
as Ur's `shell` or third-party MCP tools) continue to show as they arrive.
Keeping normalization in `toolInput.ts` respects `AGENTS.md`'s rule that
harness payloads pass through `oxd` untouched.

This replaces the prefix-only check and prefixed map keys in one small
TypeScript file and its unit test (`cmd/ox/web/toolInput.test.mjs`), with low
risk and consistent display across harnesses.

## F4. Fallback effort on a model change is computed in Go and the web client

Low · Rejected

When a model changes to one that does not offer the current effort, Ox picks
the new model's default effort (or none when the model has no efforts). That
one-line rule appears in both `internal/config/config.go:224`
(`Harness.Effort`, called from `internal/server/methods.go:732` and
`internal/server/mcp.go:652`) and `cmd/ox/web/src/SettingsFields.tsx:42`
(`ModelPicker.choose`).

### Places

- `internal/config/config.go:224` — `Harness.Effort` chooses the fallback
  effort for `oxd`.
- `internal/server/methods.go:732` — `configureSession` uses `Harness.Effort`
  when `session/configure` changes a session's model.
- `internal/server/mcp.go:652` — `startedRecord` uses `Harness.Effort` when a
  new agent-started session switches model.
- `cmd/ox/web/src/SettingsFields.tsx:42` — `ModelPicker.choose` computes the
  same fallback for draft settings.

### Defects

None.

### Evidence

Code inspection of `cmd/ox/web/src/SessionView.tsx:377` and
`cmd/ox/web/src/SettingsFields.tsx:42`. For existing sessions, `SessionView`
sends only `{ model }` to `session/configure` and lets `oxd` decide the
resulting effort; `ModelPicker.choose` only updates client-side draft state
before a session exists in `oxd`.

### Replacement

Rejected: cheaper to keep than to replace. Existing sessions already have one
authoritative owner (`oxd`), and a new-session draft has no server session yet,
so removing the one-line check from `SettingsFields.tsx` would require a
round-trip RPC just to pick a draft effort.
