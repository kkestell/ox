## F1. A relay 503 can leave Send disabled after reconnect

High · Plan

Tracked in [#84](https://github.com/kkestell/ox/issues/84).

The relay and the browser both observe events that tell them a stream has ended.
In the browser, an EventSource error or a rejected POST closes the bound stream
and starts recovery. An HTTP 503, which the relay emits when it can no longer
use that connection, fails only the request. The rest of the page reads
`Disconnected` as evidence that stream cleanup and reporting have already
happened.

During catch-up, a 503 makes the reload return early and leaves that stream
selected. Until the browser independently sees an event-stream error, there is
no new reload and Send and settings stay disabled. A 503 on an already ready
page likewise leaves readiness and other pending calls under a stream the relay
has said it cannot use. This breaks **Lost connection**.

### Places

- `cmd/ox/main.go:153` opens an event stream over a daemon connection and
  registers and removes the relay's stream ID.
- `cmd/ox/main.go:193` returns 503 when the ID is gone or writing to the daemon
  connection fails.
- `cmd/ox/web/src/connection.ts:55` closes the stream, fails its pending
  requests, and reports the error or schedules a reconnect.
- `cmd/ox/web/src/connection.ts:108` binds each POST to its stream ID. It
  rejects only the individual call on 503, while a rejected fetch for the
  current stream goes through `drop`.
- `cmd/ox/web/src/ox.tsx:566` stops retrying on `Disconnected`, relying on the
  connection to report and recover from the loss.
- `cmd/ox/web/src/ox.tsx:734` clears readiness and marks snapshots for reload
  when the connection reports a loss.
- `cmd/ox/web/src/poll.ts:13` keeps the last file answer on `Disconnected`,
  relying on the page to report the loss.

### Defects

[Deslop F7](2026-11-22-deslop-audit.md#f7-two-kinds-of-failed-request-show-no-error)
found that a rejected POST left the file panel blank or stale without a useful
connection error. [#41](https://github.com/kkestell/ox/pull/41) made rejected
fetches drop the stream. The
[page-errors plan](../plans/2026-11-22-page-errors.md#decisions) assumed that
for a 503 “the relay's `oxd` connection is gone, so the stream drops with it.”
The 503 path still relies on the browser delivering that separate event.
[#75](https://github.com/kkestell/ox/pull/75) fixed #72 by binding each reload
to its own stream. The binding resolves the cross-stream retry, while the
decision to end the current stream still differs by failure signal.

### Evidence

A temporary Playwright probe restarted the relay and returned `503 unknown
connection` once on the replacement stream's `harness/list` POST. The event
stream stayed open and the route was restored to normal after that response.
Send remained disabled after advancing the page clock three seconds. Source
tracing shows why `retry` returned without installing the catalog or starting
another stream. The existing “a lost connection keeps the last listing” spec
injects the same 503 and checks that it preserves the listing. Its subsequent
network abort independently starts a reconnect.

### Replacement

Let `connection.ts` own the end of the current stream for both EventSource
errors and terminal POST failures. It already has the stream identity needed to
ignore a failure from an ended stream. A 503 on the current stream should use
the same transition as a rejected fetch on that stream. That transition fails
pending requests, clears readiness through `onError`, and starts the existing
reconnect. A request already on an ended stream can still reject without
affecting the replacement.

This removes the path that gives the page a connection-ended error while leaving
the matching stream live. It needs a connection-layer change and an e2e check
for a 503 with the event stream still open. File polling retains its last
result, ordinary errors retain their retry behavior, and a rejected send shows
its error without resending.

## F2. A child report can reach its parent while a sibling is still running

Medium · Plan

Tracked in [#85](https://github.com/kkestell/ox/issues/85).

The parent checks the whole family's readiness under `Server.mu` and later takes
reports by visiting each child's goroutine. The state check and the queue drains
can describe different moments. A child can start after the check, then a
sibling can finish and append a report before the parent visits it. The parent
takes that new report even though the family was never eligible while the report
existed. This breaks **Child reports** and can split a group of reports into
separate parent turns.

### Places

- `internal/server/session.go:64` stores each child's untaken reports with its
  own turn state, owned by the child goroutine.
- `internal/server/session.go:513` publishes a child's state under the
  membership mutex, records the report via `report`, and pings on the applicable
  state transitions.
- `internal/server/session.go:550` makes completed reports and appends them to
  the child's queue.
- `internal/server/session.go:585` posts report delivery to the parent as a
  later operation.
- `internal/server/session.go:612` checks family membership and running state,
  releases the mutex, then posts to each child to drain its queue.

### Defects

The [child-reports plan](../plans/2026-11-23-child-reports.md#decisions)
deliberately kept reports with the child because that “keeps each child's
reports in order and leaves the parent with nothing to keep in sync.” It also
considered a child starting between the two passes and said that “either outcome
is valid.” For a batch that was already pending when the parent checked,
selecting it before the new turn is a valid ordering. The probe below produces a
report after the sibling has started, so no ordering can place that report in an
eligible batch before the new turn. The prior audit's #71 concerned suppressing
reports across turns. Its fix gives each turn its own suppression state and
leaves delivery's two passes in place.

### Evidence

A temporary race-enabled Go probe paused the parent just after the family check,
when neither child was running and there were no reports. Through ordinary
session RPCs it then started child A on a long turn, waited for its `running`
update, finished a short turn on child B, and waited for B's `idle` update.
After releasing the parent, its `session/get` history already contained B's
report. A was still running. The gate only fixed the ordering of operations
already possible on independent session goroutines.

### Replacement

Give the owner of the family membership and its published running states
ownership of the pending report queues for that membership. The child goroutine
still decides what its turn reports, including suppressing a report when
applicable. It publishes the finished report to the membership owner. The parent
takes an eligible batch in one membership operation. It then delivers the batch
to its harness from its own goroutine after releasing the lock.

This keeps each child's order without asking a parent to mirror child state. It
removes the cross-goroutine queue drains and the interval in which a new report
can join an older eligibility decision. The change touches the server's report
publication and delivery paths and their tests. It preserves the existing queue
and delivery rules and changes the premature turn the parent can start today.

## F3. The usage countdown freezes when the page disconnects

Low · Plan

Tracked in [#86](https://github.com/kkestell/ox/issues/86).

The page's clock paces requests and tells usage rows that wall time has passed.
It only advances while the page is visible and caught up. The page keeps a
session's latest subscription reading on screen while reconnecting or waiting
for Reload, so its countdown and reset styling can freeze indefinitely. The
underlying usage reading can be historical while the time remaining should still
be calculated from its recorded reset time, as **Subscription usage** describes.

### Places

- `cmd/ox/web/src/ox.tsx:724` advances the shared clock only while the page is
  visible and ready for requests. Its disconnect handler keeps the last session
  snapshots.
- `cmd/ox/web/src/poll.ts:13` uses the clock to pace file reads and folder
  listings.
- `cmd/ox/web/src/Usage.tsx:59` uses that clock to refresh `Date.now()` for the
  countdown, elapsed marker, and reset state.

### Defects

The [usage plan](../plans/2026-11-24-usage-windows.md#implementation-plan) chose
“`Date.now()` read in a memo that tracks `ox.clock()`.” Reusing the timer avoids
a timer per row. The clock's readiness gate is useful for file requests and now
also freezes a freshly added local time calculation.
[#82](https://github.com/kkestell/ox/pull/82) introduced the affected reading.

### Evidence

A temporary Playwright probe displayed the fake harness's 5-hour reading with
`80%` and `2h 0m` left, then restarted the relay and refused its event stream so
the page showed Reload. Advancing the browser clock three hours left the reading
at `5h 80% 2h 0m`. It never showed `Waiting` while the stream stayed closed.

### Replacement

Keep one page clock for visible time and let the polling path own whether it may
issue a request. Usage derives time left and expiry from that clock and the
stored reading. This keeps the plan's shared timer and removes the connection
state from the usage display's reset calculation. The change touches the clock
and polling boundary, with a browser check for a visible reading crossing its
reset while disconnected. It changes the countdown, dimmed state, and accessible
reset message during a connection loss.

## F4. A top-level session stores the same path as its workspace

Low · Rejected

A top-level session starts with the workspace's path, so two records hold the
same string. This resembles duplicated state after the session-directory change.
The workspace path identifies the registered workspace and is used by draft file
reads. The session directory records where a particular harness runs and serves
every session's file reads.

### Places

- `internal/store/store.go:173` migrates workspace paths and old child
  directories to the session directory column.
- `internal/store/store.go:266` requires an absolute session directory and
  persists it. The settings save leaves that directory alone.
- `internal/server/methods.go:310` constructs a top-level session with its
  workspace's path.
- `internal/server/mcp.go:347` resolves a child directory, which can differ from
  its workspace's path.
- `internal/server/methods.go:235` resolves file reads by their workspace or
  session selector.

### Defects

The pre-change structure used different root decisions for the file tree and the
harness. A child could see a file tree for a checkout other than the one it was
editing. [#83](https://github.com/kkestell/ox/pull/83) corrected that by making
every session's directory authoritative for both uses.

### Evidence

The [session-directory plan](../plans/2026-11-22-session-directory.md#decisions)
makes the field “fixed at creation” and removes `children.directory`. The
production writes and one-time migration establish the paths. There is no
workspace path edit or session directory edit that could make a top-level
session's pair drift. Both a child working elsewhere and a draft with no session
are supported cases and use different selectors.

### Replacement

Rejected. A selector for the current workspace and a recorded working directory
serve different purposes. Deriving the directory for only top-level sessions
would bring back the child-or-workspace rule that #83 removed, while the
equality at creation requires no ongoing synchronization.
