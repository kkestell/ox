## F1. A late child message suppresses the next turn report

High · Plan

Tracked in [#71](https://github.com/kkestell/ox/issues/71).

The MCP call and the child's harness report different parts of the same
event. The MCP goroutine knows a message arrived at the parent. The child
goroutine sees tool use, tool results, and turn boundaries. Once the parent
accepts, the MCP call posts a flag to whichever child turn is active. The
flag names neither the turn nor the particular call. The next tool result can
advance it even if it came from another tool on a different turn. The child
can then finish normally and silently omit its report to the parent, breaking
**Child reports**.

### Places

- `internal/server/mcp.go:276` accepts on the parent's goroutine, waits, then
  sets `toldSent` on the child's goroutine if the child is busy.
- `internal/server/session.go:64` keeps the unqualified `told` state beside
  the child's pending reports.
- `internal/server/session.go:541` feeds updates into `report`, which moves
  the flag on any tool result or use and consults it when the turn ends.
- `internal/claude/agent.go:222` publishes tool uses and results with their
  IDs from the harness stream. The suppression rule ignores the IDs.

### Defects

[Child reports review F2](../reviews/2026-11-23-child-reports.md#f2-a-send_message-answered-after-its-turn-suppresses-the-next-report)
showed that an MCP reply arriving after its turn ended could suppress the
following turn. #64 added a guard for the case where the child is idle at
that point. The guard cannot distinguish the original turn from a new active
one. `TestChildReports` exercises the idle case.

### Evidence

A temporary race-enabled server test held the parent's `Send` with the
existing `sendGateAgent`. While a child's MCP message was held there, the
test interrupted the original child turn and started another turn. It
released the parent, waited for the old MCP call to return, and answered the
new turn's unrelated approval. The child sent its reply. The parent received
the delayed message and a later report from the same child, with the report
from the unrelated approval turn missing. The test failed on that missing
report. This is an injected ordering on the server and fake harness. The
delay can occur while a parent is occupied or is accepting an input. There
is no measurement of how often real Claude reaches the ordering.

### Replacement

The [child reports plan](../plans/2026-11-23-child-reports.md#decisions) chose
the flag so “Ox recognizes its own call this way without reading harness
tool names.” Keep tool names out of the server's inference. Give the child
goroutine ownership of an association between the accepted parent message and
the originating turn or step. The receiving parent supplies acceptance and
the child supplies the lifetime. At minimum, the effect of a call waiting on
the parent must be bound to the child's original turn before that wait.
Confirm what call identity Claude supplies before making suppression depend
on specific tool results. The existing path exposes no matching ID on the
MCP side.

This can remove the busy check as a proxy for turn identity and the assumption
that an arbitrary tool result belongs to that call. It touches the MCP handoff,
the child's report state, and their tests. Preserve suppression when the child
really did message its parent in its final step, and keep report batching and
the MCP result unchanged. The user-visible difference is that the parent gets
the unrelated turn's report.

## F2. A retry from a closed stream enables actions early

Medium · Plan

Tracked in [#72](https://github.com/kkestell/ox/issues/72).

The connection owns the event stream and fails RPCs in flight when it drops.
The provider owns the reload, including the time between retry attempts, and
its RPC closures look up whichever stream is connected at the time. A sleeping
retry holds no connection identity and no pending RPC. If a new stream connects
before it wakes, the old reload can continue on the new stream. It can install
the catalog from the old stream together with a workspace list from the new
one, start another set of session loads, and re-enable actions even while the
current reload is still waiting for its catalog. This breaks **Lost connection**.

### Places

- `cmd/ox/web/src/connection.ts:34` owns the stream and pending calls. A drop
  rejects those calls and visibility can open a replacement immediately.
- `cmd/ox/web/src/ox.tsx:555` retries through a timer outside the stream owner,
  exiting only when an attempt receives `Disconnected`.
- `cmd/ox/web/src/ox.tsx:574` has each retrying `load` install a live snapshot.
- `cmd/ox/web/src/ox.tsx:610` reads the catalog and workspace list in separate
  attempts, then installs both, sets readiness, and starts session loads.
- `cmd/ox/web/src/ox.tsx:670` can start another load from a live
  `session/created` notification.
- `cmd/ox/web/src/ox.tsx:720` starts a reload on connect and marks cached
  sessions reloading on a drop. The earlier retry timer survives both.

### Defects

[Earlier deslop F3](2026-11-22-deslop-audit.md#f3-one-failed-snapshot-after-a-reconnect-leaves-a-session-out-of-sync)
showed that a failed snapshot left a session out of sync. #38 made snapshot
reloads retry. [#62](https://github.com/kkestell/ox/pull/62) added immediate
reopening when a waiting page becomes visible. The timer and the new stream
can now overlap under the ordering below. The earlier fix handled the failure
of one attempt and left the lifetime of the retry with the provider.

### Evidence

In a temporary Playwright spec against the real relay and daemon, I failed
`workspace/list` during one reconnect, dropped that stream while the retry
slept, then used the existing page-shown helper to reopen. I held the new
connection's `harness/list` POST. Send became enabled before the held catalog
request reached the daemon. The old reload's retry had used the new stream to
load the session. The test used the same daemon catalog across both streams.
Mixing different catalogs follows from the same code when the daemon's
configuration changes between connections.

### Replacement

The [iOS reconnect plan](../plans/2026-11-23-ios-resume-reconnect.md#related-code)
left the provider unchanged on the assumption it “already handles any number
of drops and connects.” The connection already observes exactly when its
stream ends. Let that lifetime bound the provider's reload and retry waits.
The provider still applies the catalog, list, and session snapshots, using the
same active connection for each attempt in its reload. Old work ends with the
stream, including time spent between requests. Only the active reload can
publish readiness or an error. Keep actions available as each required
snapshot arrives and keep the automatic retry for failures on the same open
stream. This needs changes in `connection.ts`, `ox.tsx`, and the reconnect
specs. It removes competing reloads across streams and readiness inferred
from whether a delayed RPC happens to find some live connection.

## F3. Messages retain the sender label at send time

Low · Rejected

The current label changes once the generated title arrives. A message sent
before that still has the first-line or short-ID label, including after a
reload. At first this looks like two owners of the label in **Session labels**.

### Places

- `internal/server/session.go:121` derives the current session label.
- `internal/server/mcp.go:669` stamps the current label on the message at
  send time and includes it in the text the receiving model gets.
- `internal/server/mcp.go:611` renders the recorded sender label for
  `read_session`.
- `cmd/ox/web/src/SessionView.tsx:266` renders the label from the same message
  record for pending and taken messages.

### Defects

None. The earlier structural audit's [F2](2026-11-20-003-since-first-audit.md#f2-a-sessions-label-is-derived-on-both-sides-of-the-protocol)
concerned separate live derivations on the server and page. The page now
reads the server's session label.

### Evidence

Traced message construction, history, and the two readers. The
[titling plan](../plans/2026-11-23-session-titles.md#decisions) explicitly
says, “A message recorded before the title arrived keeps the label it was
sent with.” The protocol describes the same snapshot.

### Replacement

Rejected. A current label and the attribution delivered with a historical
message describe different times. Resolving past message headings through the
current session would change how old messages appear and require a fallback
for deleted senders. The plan deliberately keeps that attribution stable.
