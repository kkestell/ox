Agent teams

An Ox session can now create other Ox sessions, give them work, and exchange messages with them while they run. The server runs those sessions itself, each in its own Git worktree or in a named directory, and on any model in the Ox catalog.

Orchestrators and workers

The session the user talks to is the orchestrator. The sessions it creates are its workers. A worker is an ordinary saved session. Its workspace is its worktree or directory, and a new table in the database links it to its orchestrator. Any session that was not created as a worker is an orchestrator.

Team tools are added to every session the ACP server runs. ox run does not get them, because it ends when its one prompt ends, which would stop every worker. The tools available depend on the role:

ToolOrchestratorWorkerWhat it does
create_agentyesnoCreates a worker, saves its first message, and starts its turn.
send_messageyesyesSaves a message for a worker or for orchestrator, and starts a turn on an idle worker.
list_agentsyesyesLists each member's name, model, effort, workspace, branch, and whether it is working.
remove_agentyesnoCancels the worker, removes its worktree and branch, and deletes its session.
waityesnoBlocks until a message arrives or no worker is working, then returns the waiting messages.

Workers run without a view in the terminal client. The plan's section "Next: watching workers" describes a second stage that adds one.

The parts involved

The change touches five areas. The internal/tools package declares a Team interface and the tool schemas. The internal/server package implements that interface and runs worker turns. The internal/agent package reads a session's waiting messages during a turn. The internal/store package saves team members and messages. A new internal/worktree package creates and removes worker worktrees.

The Team interface keeps the tools package independent of the server, in the same way the MCP catalog joins the tool set from outside the package. When Toolbox.Team is nil, the team tools are absent.

internal/tools/team.go

type Team interface {
	IsWorker() bool
	WorkerModels() string
	CreateAgent(context.Context, CreateAgentArgs) (string, error)
	SendMessage(ctx context.Context, to, text string) (string, error)
	ListAgents(context.Context) (string, error)
	RemoveAgent(ctx context.Context, name string) (string, error)
	Wait(context.Context) (string, error)
}

Storage

Two tables are added. The existing sessions table does not change. team_members marks a session as a worker and records its orchestrator, its name, and its branch. messages holds messages that have not yet been delivered.

internal/store/store.go

CREATE TABLE IF NOT EXISTS team_members (
    session_id TEXT PRIMARY KEY REFERENCES sessions (id) ON DELETE CASCADE,
    parent_id  TEXT NOT NULL REFERENCES sessions (id),
    name       TEXT NOT NULL,
    branch     TEXT NOT NULL,
    UNIQUE (parent_id, name)
);

CREATE TABLE IF NOT EXISTS messages (
    id        INTEGER PRIMARY KEY,
    recipient TEXT NOT NULL REFERENCES sessions (id) ON DELETE CASCADE,
    sender    TEXT NOT NULL,
    text      TEXT NOT NULL
);

parent_id has no cascade, so the database refuses to delete an orchestrator that still has workers. Deleting a worker session removes its team_members row and its messages. branch is empty for a worker that uses a directory instead of a worktree.

Store.List now leaves out workers, so the session picker shows only sessions the user started. A worker's title is its name.

Messages are saved rather than kept in memory, so a report that arrives while the orchestrator is idle survives a restart. Store.Take reads a recipient's messages and deletes them in one transaction.

Delivering messages during a turn

Before: hook context

Before this change, hooks could add text to a turn in three places: at turn start, after each tool call, and at stop. The text was saved in a HookContext field on TurnStart and AssistantBatch, and sent to the model as a user message. transcript.HookMessage joined the items and added the label "Context added by the user's hooks:" in front of them.

After: context from several sources

Messages use the same three places and the same transcript fields, so saving, provider requests, replay, and display need no new paths. The fields are renamed from HookContext to Context, and the agent.HookContext event to agent.Context. Since an item can now come from a hook or from a message, each item names its own source. The hook label moves to where hook output is collected, and transcript.ContextMessage only joins the items.

internal/transcript/transcript.go, before

func HookMessage(context []string) string {
	return "Context added by the user's hooks:\n\n" + strings.Join(context, "\n\n")
}

internal/transcript/transcript.go, after

func ContextMessage(context []string) string {
	return strings.Join(context, "\n\n")
}

internal/agent/hooks.go, after

func hookContext(texts []string) []string {
	if len(texts) == 0 {
		return nil
	}
	return []string{"Context added by the user's hooks:\n\n" +
		strings.Join(texts, "\n\n")}
}

The inbox

agent.Input gets an Inbox field of type func() []string. It takes the session's waiting messages, each already formatted as the model reads it: 

Message from <name>:
<text>

The turn calls the inbox at each place hooks add context:

PlaceSaved inEffect
Turn start, after the prompt hooksTurnStart.ContextThe messages follow the user's input.
After each tool call, after the PostToolUse hooksAssistantBatch.ContextThe messages follow the tool results.
When the model finishes, after the Stop hooksAssistantBatch.ContextThe turn continues, as it does when a Stop hook blocks.

The stop case changes the most. Before, only Stop hook reasons could continue a turn. Now any added context continues it, and the turn ends only when the Stop hooks allow it and the inbox is empty. stopHookActive still tracks only the hooks, since it is passed to the Stop hooks themselves.

A nil Inbox delivers nothing. ox run sets no inbox and no team, so its turns behave as before.

Running a turn from the server

Before: only ACP prompts started turns

Before this change, the ACP prompt handler started a goroutine that prepared the MCP catalog, called agent.Start, and ran the turn. That code lived inline in the handler, and no other path started a turn.

After: one turn function for both callers

The goroutine body moves into Server.runTurn. ACP prompts and worker turns both call it with a session, an input, and an agent.Client. It builds the session's Team and its Inbox, which reads from the store.

internal/server/server.go

turn, err := s.agent.Start(ctx, agent.Input{
	SessionID: id, Input: input,
	Model: selections.Model, Effort: selections.Effort,
	SystemPrompt: session.systemPrompt,
	Processes: session.processes, MCP: catalog,
	Team: team, SessionStart: !started,
	Inbox: func() []string {
		messages, err := s.takeMessages(id)
		inboxErr = errors.Join(inboxErr, err)
		return messages
	},
}, client)

Callers of runTurn hold the session's prompt operation from operations, which allows one operation per session at a time. A worker therefore runs at most one turn at a time, and the operation also tells list_agents and wait whether a worker is working.

Starting a worker turn

Server.wake(id) starts a turn for an idle worker that has waiting messages. It tries to acquire the prompt operation. If the worker is busy, the attempt fails and wake returns without doing anything; the running turn reads the new messages through its inbox. If the worker is idle, wake takes the messages and uses them as the turn's input, so they are saved as the turn's user message.

A worker turn uses workerClient, which discards events and approves every tool call, so a worker always runs in Auto mode. When the turn ends, the goroutine saves a report for the orchestrator, releases the operation, and calls wake again. The second call starts a new turn if a message arrived after the turn's last inbox call but before the turn ended.

internal/server/team.go

go func() {
	defer s.prompts.Done()
	result, err := s.runTurn(ctx, id,
		transcript.TurnInput{Message: new(transcript.TextMessage(
			strings.Join(messages, "\n\n")))},
		session, workerClient{})
	s.mu.Lock()
	if !s.removing[id] {
		if err := s.agent.Store.Send(member.Parent, member.Name,
			workerReport(member.Name, result, err)); err != nil {
			fmt.Fprintln(os.Stderr, "saving worker report:", err)
		}
	}
	s.mu.Unlock()
	release()
	s.change()
	if err := s.wake(id); err != nil {
		fmt.Fprintln(os.Stderr, "waking worker:", err)
	}
}()

The report depends on how the turn ended:

  • Finished: "Worker <name> finished its turn:" followed by the final answer.
  • Cancelled, stopped at the output limit, or refused: one line saying so.
  • Failed: "Worker <name> failed:" followed by the error.

A turn cancelled by remove_agent sends no report. The removing map records those workers.

Where a message goes

A saved message reaches its recipient by one of these paths:

The orchestrator waits

The server never starts a turn on the orchestrator. ACP has no turn that the agent starts, and the client would receive updates with no prompt running. The orchestrator calls wait after giving out work instead.

To wake waiting calls, the server keeps a channel in Server.changed. Server.change closes it and replaces it with a new one whenever a message is sent or a worker turn ends. Closing a channel releases every goroutine blocked on it.

internal/server/team.go

func (s *Server) change() {
	s.mu.Lock()
	close(s.changed)
	s.changed = make(chan struct{})
	s.mu.Unlock()
}

Team.Wait loops. It reads the current channel, takes the orchestrator's messages, and returns them if there are any. If there are none and no worker is working, it returns "No messages and no workers are working." Otherwise it blocks until the channel closes or the prompt is cancelled, then repeats. It reads the channel before taking messages, so a report saved between those two steps closes a channel that wait already holds.

A full exchange

Creating a worker

create_agent takes name, message, and optional model, effort, and dir. The name uses lowercase letters, digits, and hyphens, is unique in the team, and is not orchestrator. Model and effort default to the orchestrator's and are checked with agent.ModelSelection.

The worker's system prompt is the normal one followed by a "Team" section. That section gives the worker's name, workspace, branch, and the team at creation. It also states that the worker commits on its branch and the orchestrator merges it, or, without a worktree, that the worker follows the orchestrator's instructions about branches and commits. It states that the worker's final answer is sent to the orchestrator when its turn ends.

In Ask mode, create_agent needs permission, because the worker runs commands without asking. The permission request shows the name, model, effort, directory, the orchestrator's workspace, and the message. The other team tools need no permission.

The optional global setting workerModels is free text that describes which models workers should use and when. It is appended to the create_agent description as written. A workspace settings file that sets it is rejected.

Worktrees

Without dir, the worker gets a Git worktree. The internal/worktree package is ported from Hypercube's workspace.go and keeps only finding the checkout root, adding and removing a worktree, and the removal check.

  • The branch is ox/<name>, created from the orchestrator's HEAD.
  • The worktree is at <checkout>/.ox/worktrees/<name>. /.ox/worktrees/ is added to the checkout's .git/info/exclude.
  • When the orchestrator's workspace is a subdirectory of the checkout, the worker's workspace is the same subdirectory of its worktree.

With dir, the worker uses an existing directory: an absolute path, a path starting with ~/, or a path relative to the orchestrator's workspace. . is the orchestrator's own workspace. No branch is created, and removal leaves the directory in place. Outside a Git checkout, dir is required.

remove_agent cancels the worker's turn and waits for it to end. It then checks the worktree: removal fails if the branch is not merged into the orchestrator's HEAD or the worktree has uncommitted changes or untracked files, and the tool returns that reason to the model. If the check passes, it removes the worktree and branch, stops the worker's background processes and MCP servers, and deletes the worker's session and messages. If Git refuses, the worker stays, now idle.

internal/worktree/worktree.go

func Removable(root, dir, branch string) error {
	if _, err := git(root, "merge-base", "--is-ancestor",
		branch, "HEAD"); err != nil {
		return fmt.Errorf("branch %s is not merged into HEAD", branch)
	}
	dirty, err := Dirty(dir)
	if err != nil {
		return err
	}
	if dirty {
		return fmt.Errorf("worktree %s has uncommitted changes", dir)
	}
	return nil
}

Session lifecycle

EventEffect on the team
The orchestrator's session is closedWorkers keep running. Their reports are saved for the orchestrator.
The orchestrator's session is deletedThe request fails with "remove the session's workers before deleting it" while it has workers.
The server shuts downWorker turns are cancelled with every other prompt. Their cancellation reports are saved.
The orchestrator's session is loadedThe server calls wake for each worker, which starts a turn for any worker with waiting messages.

A worker becomes active the first time it is woken and stays active until it is removed or the server shuts down. When the server activates a worker again after a restart, its model and effort come from its latest saved turn start.
