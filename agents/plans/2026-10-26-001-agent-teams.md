# Agent teams

## Goal

Let an Ox session create other Ox agents, give them work, and exchange messages
with them while they run, as Hypercube does with tmux, hooks, and MCP. Each
agent can use any model in the Ox catalog.

The session the user talks to is the orchestrator. The agents it creates are its
workers. A worker is an ordinary Ox session that the server runs itself, in its
own Git worktree or in a directory the orchestrator names. Workers cannot create
workers.

This plan covers the first stage: workers run without a view in the terminal
client. The section "Next: watching workers" describes the second stage.

## Related code

- `internal/server/server.go` owns sessions, `prompt`, close, delete, and
  shutdown; `internal/server/operations.go` allows one operation per session.
- `internal/agent/agent.go` runs a turn. `internal/agent/hooks.go` adds context
  at turn start, after each tool call, and at stop.
- `internal/transcript/transcript.go` saves that context in `HookContext` on
  `TurnStart` and `AssistantBatch`. `internal/openrouter/messages.go`,
  `internal/openai/messages.go`, and `internal/server/convert.go` send and show
  it.
- `internal/tools/tools.go` owns tool schemas, dispatch, titles, and Ask mode
  permission. `internal/tools/mcp.go` shows how a catalog from outside the
  package joins the tool set.
- `internal/store/store.go` owns the database.
- `internal/sysprompt/sysprompt.go` builds each session's system prompt.
- `~/projects/hypercube/internal/workspace/workspace.go` creates and removes
  worktrees; `~/projects/hypercube/internal/hook/hook.go` holds the team
  instructions the agents read.

## Decisions

### Workers are sessions

A worker is a saved session whose workspace is its worktree or directory. A new
`team_members` table links it to its orchestrator, so the existing `sessions`
table and existing databases need no change:

```sql
CREATE TABLE IF NOT EXISTS team_members (
    session_id TEXT PRIMARY KEY REFERENCES sessions (id) ON DELETE CASCADE,
    parent_id  TEXT NOT NULL REFERENCES sessions (id),
    name       TEXT NOT NULL,
    branch     TEXT NOT NULL,
    UNIQUE (parent_id, name)
);

CREATE TABLE IF NOT EXISTS messages (
    id        INTEGER PRIMARY KEY,
    recipient TEXT NOT NULL REFERENCES sessions (id) ON DELETE CASCADE,
    sender    TEXT NOT NULL,
    text      TEXT NOT NULL
);
```

`branch` is empty for a worker without a worktree. `parent_id` has no cascade,
so the database refuses to delete an orchestrator that still has workers. `List`
leaves out workers, so the session picker shows only sessions the user started.
A worker's title is its name.

Messages are saved so that a report that arrives while the orchestrator is idle
survives a restart. A message is removed when it is taken for delivery. If the
turn then fails to save it, the message is lost, as hook context is today.

### Where team tools are available

Every session the ACP server runs gets the team tools. `ox run` does not: it
runs no server and ends when its one prompt ends, which would stop every worker.

- The orchestrator gets `create_agent`, `send_message`, `list_agents`,
  `remove_agent`, and `wait`.
- A worker gets `send_message` and `list_agents`.

Any session without workers is an orchestrator. A session becomes a worker only
when it is created as one.

### Delivery

`agent.Input` gets `Inbox func() []string`, which takes the session's waiting
messages, each already written as the model reads it:

```text
Message from <name>:
<text>
```

The turn calls it at the three places where hooks add context: at turn start,
after each tool call, and at stop. Messages at stop continue the turn, as a
blocking Stop hook does. A nil `Inbox` delivers nothing, as in `ox run`.

Messages travel in the same transcript fields as hook context, so saving,
provider requests, replay, and display need no new paths. The fields are renamed
from `HookContext` to `Context`, and the `agent.HookContext` event to
`agent.Context`. Each item names its own source: hook items start with "Context
added by the user's hooks:", and messages start with "Message from". The
function that joins the items for the model, `transcript.HookMessage`, becomes
`transcript.ContextMessage` and only joins them.

### Running workers

The server starts a worker's turns itself. The goroutine in `prompt` becomes one
function that runs a turn for a session with an input and an `agent.Client`. ACP
prompts and workers both use it, and it takes the same per-session operation
from `operations`, so a worker runs at most one turn at a time.

`wake(id)` starts a turn for an idle worker that has waiting messages. The
turn's input is the messages, so they are saved as its user message. When the
worker is busy, `wake` does nothing, and the running turn delivers the messages.
After every worker turn, the server calls `wake` again. This catches a message
that arrived after the turn's last delivery but before it ended.

A worker runs in Auto mode. Its client discards events and never asks for
permission, like the headless client of `ox run`. Its model and effort come from
`create_agent` on the first turn, and from its latest turn start after that, as
`loadSession` does. A worker becomes active the first time it is woken and stays
active until it is removed or the server shuts down.

### Reports

When a worker's turn ends, the server sends the orchestrator a message:

- finished: "Worker <name> finished its turn:" followed by its answer.
- cancelled, stopped at the output limit, or refused: one line saying so.
- failed: "Worker <name> failed:" followed by the error.

A turn cancelled by `remove_agent` sends no report.

### The orchestrator waits

The server never starts a turn on the orchestrator. ACP has no turn that the
agent starts, and the client would receive updates with no prompt running.
Instead:

- `wait` blocks until a message arrives or no worker is working, then returns
  the waiting messages. With no messages and no working workers it returns at
  once and says so. Cancelling the prompt cancels it.
- Messages that arrive while the orchestrator is idle are delivered when the
  user next prompts it.

To wake waiting calls, the server keeps a channel that it closes and replaces
whenever a message is sent or a worker turn ends. `wait` checks the store, then
waits on that channel or the prompt's cancellation.

### Worktrees

Port Hypercube's `workspace.go` to `internal/worktree`, keeping only what the
team needs: finding the checkout root, adding and removing a worktree, and the
removal check.

- Branch `ox/<name>` from the orchestrator's `HEAD`.
- Worktree at `<checkout>/.ox/worktrees/<name>`. `/.ox/worktrees/` is added to
  the checkout's `.git/info/exclude`.
- When the orchestrator's workspace is a subdirectory of the checkout, the
  worker's workspace is the same subdirectory of its worktree.
- Removal refuses a worktree with uncommitted changes or a branch not merged
  into the orchestrator's `HEAD`, and returns Git's reason to the model.

`dir` gives the worker an existing directory instead: an absolute path, a path
starting with `~/`, or a path relative to the orchestrator's workspace. `.` is
the orchestrator's own workspace. Ox creates no branch and leaves the directory
in place on removal. Outside a Git checkout, `dir` is required.

### Tools

- `create_agent(name, message, model?, effort?, dir?)` creates the worker, saves
  `message` for it, and wakes it. `message` is required, since a worker without
  work does nothing. `name` is lowercase letters, digits, and hyphens, unique in
  the team, and not `orchestrator`. `model` and `effort` default to the
  orchestrator's and are checked with `agent.ModelSelection`. The description
  includes the global `workerModels` setting, if any. It returns the worker's
  name, workspace, and branch.
- `send_message(to, text)` saves a message for a worker or for `orchestrator`
  and wakes the recipient if it is an idle worker.
- `list_agents()` returns each member's name, model, effort, workspace, branch,
  and whether it is working.
- `remove_agent(name)` cancels the worker's turn and waits for it, checks its
  worktree, removes the worktree and branch, stops its background processes and
  MCP servers, and deletes its session and messages. If Git refuses, the worker
  stays, now idle.
- `wait()` as described above.

The tools package declares the interface the server implements, as it does for
the MCP catalog. `Toolbox` gets a `Team` field; when it is nil, the team tools
are absent.

In Ask mode, `create_agent` needs permission, since the worker runs commands
without asking. The request shows the name, model, effort, directory, and
message. The other team tools need none: Git refuses removal of unmerged or
uncommitted work.

### Instructions

The tool descriptions carry the orchestrator's instructions, adapted from
Hypercube's `facts`: give a worker a worktree when it will change files, merge
its branch from the orchestrator's checkout and then remove it, run only
independent work in parallel, use `dir` `.` for a worker that only reads, and
call `wait` after giving out work.

A worker's system prompt is the normal one followed by a team section: its name,
its workspace and branch, the team at creation, that it commits on its branch
and the orchestrator merges, or that it follows the orchestrator's instructions
about branches and commits when it has no worktree, and that its final answer is
sent to the orchestrator when its turn ends.

### Settings

`workerModels` is optional free text in the global settings file that describes
the models the orchestrator can give workers and when to use each, like
Hypercube's `models`. It is added to `create_agent`'s description as written.

### Lifecycle

- Closing the orchestrator's session leaves its workers running. Their reports
  wait for it.
- Deleting a session that has workers fails and says to remove them first.
- Shutdown cancels worker turns with every other prompt. Their cancellation
  reports are saved, so the resumed orchestrator learns which workers stopped.
- Loading an orchestrator wakes each of its workers that has waiting messages.

## Implementation plan

1. **Rename hook context to context.** Rename the transcript fields, the agent
   event, and `HookMessage` as described in "Delivery". Move the "Context added
   by the user's hooks:" label to where hook outputs are collected. Update the
   providers, `convert.go`, and their tests. Behavior is unchanged.
2. **Store.** Add the two tables. Add
   `CreateWorker(parent, name, workspace,
   branch)`, `Members(parent)`,
   `Member(id)` returning the worker's parent, name, and branch,
   `Send(recipient, sender, text)`, `Take(recipient)`, which reads and deletes
   in one transaction, and `HasMessages(recipient)`. `List` leaves out workers.
   Test the cascade on worker deletion and the refusal on orchestrator deletion.
3. **Delivery in the turn.** Add `Inbox` to `agent.Input` and call it at turn
   start, after each tool call, and at stop, where messages continue the turn.
   Test each place with a fake provider.
4. **Worktrees.** Create `internal/worktree` from Hypercube's `workspace.go` and
   its tests, with the branch and path names above and the subdirectory mapping.
5. **Team tools.** Create `internal/tools/team.go` with the `Team` interface,
   the schemas and descriptions, argument decoding, dispatch, titles, and
   `PermissionAgent`. Show the permission in `permissionRequest`. Test that the
   schemas match the role and that bad arguments fail.
6. **Running workers.** In `internal/server`, move the prompt goroutine into one
   turn function. Add `team.go` with the `Team` implementation, `wake`, reports,
   the change channel for `wait`, removal, and waking workers on load. Refuse
   deleting a session with workers. Build the worker's system prompt section.
   Add `workerModels` to `internal/settings`.
7. **README.** Add a short section on teams: what the orchestrator can do, where
   worktrees and branches go, and `workerModels`.

## Hypercube team for this work

Run the tasks with a Hypercube team in two rounds. Tasks that change the same
files go to one worker, one after another.

| Agent         | Model                        | Work                                                                        |
| ------------- | ---------------------------- | --------------------------------------------------------------------------- |
| orchestrator  | Claude Opus, high            | Hands out work, merges, runs `make check` on `main`, and reviews each merge |
| `context`     | Codex gpt-6.1-sol, high      | Task 1, then task 3                                                         |
| `foundations` | Ox with DeepSeek Flash, high | Task 2, then task 4                                                         |
| `tools`       | Codex gpt-6.1-sol, medium    | Task 5                                                                      |
| `server`      | Codex gpt-6.1-sol, high      | Tasks 6 and 7, in the second round                                          |
| `review`      | Claude Opus, high, `dir` `.` | Reviews the merged change against this plan after the second round          |

Round 1 runs three workers in parallel, each in its own worktree:

- `context` does tasks 1 and 3, since both rewrite `internal/agent/agent.go`.
- `foundations` does tasks 2 and 4, two small packages nothing else touches.
- `tools` does task 5. It defines the `Team` interface itself. It shares
  `internal/server/convert.go` with task 1, but changes a different function.

The orchestrator merges each branch into `main` as it finishes, runs
`make check`, and removes the worker.

Round 2 starts after all three are merged. `server` does tasks 6 and 7, which
build on every earlier task and touch most of `internal/server`, so they stay
with one worker. `review` then reads the merged change in the orchestrator's
checkout with a different model from the one that wrote it. The orchestrator
sends its findings back to `server`, or to a new worker if `server` has been
removed.

Commit this plan before starting, since worktrees are created from `HEAD`. Start
the orchestrator with:

> Implement `agents/plans/2026-10-26-001-agent-teams.md`. Round 1, in parallel:
> worker `context` does tasks 1 then 3; worker `foundations` (Ox, DeepSeek
> Flash) does tasks 2 then 4; worker `tools` does task 5. Once all three are
> merged into `main`, worker `server` does tasks 6 and 7. Each worker follows
> `AGENTS.md`, runs `make check` before committing, and reports any check that
> fails. Merge each branch into `main` locally, run `make check` on `main`, then
> remove the worker. Never push worker branches. After round 2, start a
> read-only `review` worker in your checkout to review the full change against
> the plan, and send its findings back for fixes.

## Test plan

- Server tests with a temporary Git repository and the fake OpenRouter server:
  - `create_agent` creates the worktree and branch, and the worker's turn starts
    with the message.
  - The orchestrator's `wait` returns the worker's report.
  - A message to a busy worker arrives after its next tool call.
  - A message sent as a worker's turn ends starts another turn.
  - `remove_agent` refuses an unmerged branch and removes a merged one.
  - Deleting an orchestrator with workers fails.
  - Loading an orchestrator wakes a worker with waiting messages.
- `create_agent` with `dir`, and without `dir` outside a Git checkout.
- Ask mode asks before `create_agent` and runs the worker in Auto mode.
- Manually: in a scratch repository, ask the orchestrator to split a change
  between two workers on different models, merge both, and remove them; quit
  during a worker's turn and resume.

## Next: watching workers

The second stage lets the user watch a worker in the terminal client and prompt
it directly. It adds to this stage without rewriting it:

- A worker's client sends its events to the ACP connection, tagged with the
  worker's session ID, while the user is watching it. The client already filters
  updates by session.
- The client lists the team and switches its view to a member, as it switches
  sessions today.
- The server lets a session be opened during its turn. Replay covers only saved
  entries, so the server also keeps the current batch's events in memory and
  replays them, or the view accepts the gap until the next batch.
- Opening a worker skips the check that a session's workspace matches the
  client's directory.
- A prompt to an idle worker runs as a normal prompt. A prompt to a busy worker
  is saved as a message from the user.
