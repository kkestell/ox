# Shell tool for Ur

## Goal

Ur chats without tools and takes only the `manual` permission mode. Give it one
tool, `shell`, which runs a bash command in the session's workspace directory
and returns the command's output and exit status. Tool calls reach the
transcript as `tool_use` and `tool_result` updates, `manual` asks before each
command through the existing approval card, the `auto` mode runs
commands without asking, and Stop or an interrupt kills the running command's
process group. Resolves [#11](https://github.com/kkestell/ox/issues/11).

## Decisions

### Wire format

Observed live against the three built-in models with their pinned providers
(probe results):

- Each response may hold several tool calls, as `delta.tool_calls[]` fragments
  keyed by `index`. The first fragment of an index carries `id`,
  `type: "function"`, `function.name`, and `function.arguments: ""`; later
  fragments carry only `index` and more `function.arguments`. `read`
  concatenates arguments per index and returns the calls in index order.
- `finish_reason` is `tool_calls` and arrives in two consecutive chunks; `read`
  already ends on `[DONE]` or EOF after the first finish, and ignores the
  second. A response with calls yields them whatever its finish reason. A call
  missing `id` or `function.name` fails the turn with
  `OpenRouter sent a tool call without an id or name`.
- Content text may precede the calls in the same response (Muse); it streams as
  `text_delta` as today.
- No model needs `reasoning_details` passed back, and an assistant message with
  `tool_calls` may omit `content`. Ur keeps ignoring reasoning.
- Every assistant `tool_calls` message must be followed by one `tool` message
  per call ID: Muse and OpenAI refuse the request with HTTP 400 otherwise (see
  the table below).
- Every request carries `tools: [shellTool]`.

`message` gains the OpenAI fields, and `Content` becomes `omitempty`:

```go
type message struct {
	Role       string     `json:"role"`
	Content    string     `json:"content,omitempty"`
	ToolCalls  []toolCall `json:"tool_calls,omitempty"`
	ToolCallID string     `json:"tool_call_id,omitempty"`
}

type toolCall struct {
	ID       string `json:"id"`
	Type     string `json:"type"` // "function"
	Function struct {
		Name      string `json:"name"`
		Arguments string `json:"arguments"`
	} `json:"function"`
}
```

The JSONL file stores these messages as they go on the wire, one per line, as
it does today: each text delta as an assistant entry, then the response's calls
as one assistant entry `{"role":"assistant","tool_calls":[...]}` saved when the
stream ends, then each command's outcome as a tool entry
`{"role":"tool","tool_call_id":"...","content":"..."}` saved when it is known.
Existing files read unchanged.

`conversation` stays the one place that turns history into a request. It joins
each run of assistant entries into one message, concatenating `content` and
appending `tool_calls`, and answers every call that has no tool entry before
the next user entry with a tool message whose content is `stopped`:

```go
// stopped answers a call whose command did not finish: an interrupt, Stop, or
// oxd exiting during it.
const stopped = "The user stopped this command before it finished."
```

This one rule keeps every request valid after an interrupt, a Stop, or `oxd`
dying mid-command, with no save on those paths. The wording discourages the
model from rerunning the command, which it does when told only `Interrupted`.

Live check of the rule: a history of a user prompt, an assistant `tool_calls`
message running `touch done.txt && echo created`, then a new user prompt asking
whether the command ran and created the file. (a) has no tool message for the
call; (b) has the `stopped` tool message before the new prompt. Each was sent
non-streamed with `tools` and `reasoning.effort` `low`, the built-in models
pinned to their configured providers.

| Model                                          | (a) unanswered                                         | (b) `stopped`                                  |
| ---------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------- |
| `deepseek/deepseek-v4.1-flash-1017` (built-in) | 200; claims it ran and printed `created`               | 200; stopped, cannot confirm the file          |
| `z-ai/glm-5.3-flash` (built-in)                | 200; claims it ran and created the file                | 200; stopped, file likely not created          |
| `meta/muse-spark-1.3-contributor` (built-in)   | 400 `No tool output found for function call call_ox1.` | 200; stopped, cannot confirm the file          |
| `openai/gpt-6.2-sol`                           | 400 `No tool output found for function call call_ox1.` | 200; started but stopped, cannot confirm       |
| `anthropic/claude-haiku-5.5`                   | 200; output was `...`, cannot confirm                  | 200; stopped, file may not exist               |
| `google/gemini-4-hydrogen`                     | 200; claims it ran and created the file                | 200; stopped, unknown whether the file exists  |
| `qwen/qwen3.8-flash`                           | 200; saw no output, cannot confirm                     | 200; stopped, cannot confirm without checking  |

Every model accepts (b) and treats the command as stopped and its effect
unconfirmed, so the rule stands as written. Without it, two models refuse the
request and three claim the command succeeded.

### The tool

`internal/ur/shell.go` owns the tool: its schema, argument parsing, and
`runShell(ctx, workspace, args) outcome`, where
`outcome struct{ text string; isError bool }`.

Schema: name `shell`; `command` (string, required); `timeout_seconds`
(integer, 1–600, default 120); `additionalProperties: false`. The description
says it runs `bash -c` in the session's workspace with stdin from `/dev/null`,
each call in a fresh shell, and returns the exit status and the start and end
of the combined output, at most 16 KiB.

Arguments are checked when the call comes up, before any approval: invalid
JSON, a missing or non-string `command`, an unknown field, or a
`timeout_seconds` outside 1–600 answer the call at once with an error outcome
(`arguments: ...`) and no approval. A call to any other tool name answers
`Ur has no tool "<name>"`. The `tool_use` update's `input` is the arguments when
they are a JSON object, else `{}`.

Running:

- `exec.CommandContext(ctx, "bash", "-c", command)` with `ctx` the turn's
  context bounded by the timeout, `Dir` the workspace,
  `SysProcAttr{Setpgid: true}`, `Cancel` sending SIGKILL to the whole group,
  and `WaitDelay` one second, so a descendant holding the output pipe cannot
  hold the call. After `Wait` returns, for any reason, the group gets SIGKILL
  too, which ends background children the command left; `ESRCH` is ignored.
- `Env` is `os.Environ()` without `OPENROUTER_API_KEY`.
- stdout and stderr share one writer: a capture that keeps the first 8 KiB and
  the latest 8 KiB, counting the bytes between, as prior art's `Capture` does
  for one stream. Invalid UTF-8 becomes U+FFFD.
- The outcome text is a status line, a blank line, then the output or
  `(no output)`, with `[... N bytes omitted ...]` between the head and tail
  when the middle was dropped. The status is `Exit code: N`,
  `Terminated by signal: N`, or `Timed out after N seconds`. A start failure
  is `Could not start bash: <err>`. Only exit code 0 is not an error.
- A canceled turn's outcome is never used (see Ownership), so `runShell` does
  not report cancellation.

### Turn steps

`turn` gains the context its request and command watch, and its step:

```go
type turn struct {
	prompt string // the ID of the input whose turn it is; a later input taken into the turn replaces it
	ctx    context.Context
	cancel context.CancelFunc
	step   step
}

//sumtype:decl
type step interface{ isStep() }

type streaming struct{}  // the request is streaming
type asking struct {     // calls[0] waits on this approval
	calls     []toolCall
	requestID string
	request   json.RawMessage
}
type executing struct{ calls []toolCall } // calls[0]'s command runs
```

`calls` is the response's calls not yet answered, oldest first. A pending
approval exists only inside `asking`, so `Snapshot().Approvals` is derived from
the step: one `agent.Approval{RequestID, Request, ToolName: "shell"}` while
asking, else none.

Flow, all on the session goroutine:

- `ended` carries the response's calls. With an error, the turn finishes with
  it. With no calls, it finishes with the reply as today. With calls, Ur saves
  the assistant `tool_calls` entry and calls `next(calls)`.
- `next(calls)`: with no calls left, Ur takes every queued input into the turn
  (saving each as a user entry, and setting `turn.prompt` to the last), sets
  `streaming`, and posts the next request. Otherwise it publishes `tool_use`
  for `calls[0]` and checks its arguments; an invalid call is answered at once.
  In `auto` it sets `executing` and starts the command. In
  `manual` it sets `asking` with a fresh `rand.Text()` request ID, reports
  `requires_action`, and publishes `approval` with
  `{"tool_name":"shell","input":<arguments>,"tool_use_id":"<call id>"}`.
- `answer(calls, outcome)`: saves the tool entry, publishes `tool_result` with
  the outcome's text and `is_error`, then `next(calls[1:])`. A failed save
  finishes the turn with `Ur could not save the command's result: <err>`, as a
  failed reply save does.
- `Approve(requestID, response)`: refuses a response whose `behavior` is not
  `allow` or `deny` with `response must be an allow or deny permission
  response`, and an ID that is not the asking step's with
  `agent.ErrApprovalNotFound`. It publishes `approval_answered` and reports
  `running`. Allow sets `executing` and starts the command as the model wrote
  it; the card's `updatedInput` is that same input. Deny answers with
  `The user denied this command: <message>` as an error.
- The command runs on a goroutine that delivers
  `ran{turn, callID, outcome}`; `Handle` drops it unless the turn and step
  still match, then calls `answer`.

Calls in one response run one after another, so at most one approval is
pending and one command runs. The turn's `result` text is the last assistant
message's content, as today.

### Permission modes

Ur takes `manual` ("Manual"), which asks Allow or Deny for every shell call,
and `auto` ("Auto"), which allows every call: the same IDs and names as
Claude's. `checkPermissionMode` accepts those two and refuses `acceptEdits` and
`plan`; `default.json` lists `{ "id": "auto", "name": "Auto" }` after Manual.
Sharing Claude's IDs lets an Ur child of a Claude session in `manual` or `auto`
take its parent's mode. Ur sessions stored with `manual` keep it unchanged.

A new Ur session's mode follows the new-session form's existing rule
(`NewSessionView.tsx`, `defaultPermissionMode`): the draft keeps its mode when
Ur offers it, and otherwise takes Ur's first listed mode, Manual. The
configured defaults name Claude, so they do not apply.

The mode is read from `a.settings` when each call comes up; `Configure`
already refuses while a turn runs, so a mode never changes under a pending
call. Existing configuration files keep listing only Manual for Ur until the
user edits them; the built-in catalog changes for new files.

### Interrupt and Stop

- `Interrupt` while asking publishes `approval_cancelled`; while asking or
  executing it publishes `tool_result` for `calls[0]` with `stopped` as an
  error; then `finish` publishes the `Interrupted` result and `idle` and
  cancels the turn's context, which kills the command's group through
  `Cancel`. Order: `prompt_cancelled` for each untaken input,
  `approval_cancelled`, `tool_result`, `result`, `state idle`.
- `Stop` while asking publishes `approval_cancelled`, then cancels and
  publishes `exited` as today; the client marks the open tool call stopped.
- Calls not yet reached never got a `tool_use`, so nothing in the transcript
  waits on them; `conversation` answers them with `stopped` in the next
  request.

### Concerns

- **Requirements:** *Tool calls* holds: `tool_use` then `tool_result`, or
  `exited` marking it stopped. *Permission requests*, *Allow and Deny*,
  *Approvals wait*, and *One answer per approval* hold through the derived
  approval: it shows on every page and after a reload from `Snapshot`, is
  withdrawn on interrupt, idle, or Stop, and a second answer finds no matching
  step. The session does not park while asking, since the tracker reports
  `requires_action` and `Parkable` is `tracker.Idle()`. *One prompt at a time*
  now applies to Ur's steps: a prompt sent during a tool loop is taken after
  the current command's result, before the next request, and a prompt sent
  during the last streamed reply runs next. *Stop* ends the command with the
  turn. *Settings shown are settings used* holds since the mode is read per
  call and changes only while idle. *Stopping oxd* covers Ur's commands (see
  Settling). *Ur sessions* changes (see Requirement changes).
- **Settings:** the mode reaches no process; Ur reads it per call. A mode Ur
  does not honor is refused by `checkPermissionMode`, at startup for the
  configuration and per request.
- **Settling:** a command ends by exiting, its timeout (at most 600 s), or the
  turn's cancellation; output reading ends at most one second after any of
  those through `WaitDelay`. An approval waits for an answer by design and
  ends on interrupt or Stop. `oxd`'s shutdown waits for every command
  goroutine: a package `sync.WaitGroup` counts them, and `ur.WaitAll`, called
  in `cmd/oxd/main.go` after `claude.WaitAll`, returns once each has killed
  its group and returned. Stop cancels every turn first, so the wait is about
  a second. A command goroutine's delivery ends on the session reading it or
  on `a.done`.
- **Process I/O:** output is captured to EOF or one second past the command's
  end, combined in arrival order; a start failure's reason reaches the model
  and transcript as the outcome text.
- **Construction:** an approval exists only inside `asking`, and a running
  command only inside `executing`, so neither can outlive its step or coexist
  with the other. Every request is valid because `conversation` alone builds
  it and answers unanswered calls. The tool result the model reads and the one
  the transcript shows are the same `outcome`, saved and published by
  `answer`.
- **Ownership:** the turn's step is owned by the session goroutine through the
  agent; it is set by `ended`, `Approve`, `ran`, and cleared by `finish` and
  `Stop`. A late `ran` or `ended` from a canceled turn fails the turn and step
  check and is dropped. The command goroutine owns its process and reads only
  its arguments. The `WaitGroup` is the one package state, needed for
  *Stopping oxd*; it is only added to and waited on. No field is stored beyond
  the JSONL entries above.
- **Claude Code:** not touched.
- **Trust boundaries:** commands run as `oxd`'s user, with its environment
  minus `OPENROUTER_API_KEY`, starting in the workspace and able to reach any
  path that user can. The model triggers them, gated per command in `manual`
  and ungated in `auto`, the mode the user picks. Messages from
  other sessions can start Ur turns, as they start Claude's.

   - **Old:** "Ur chats through OpenRouter with the user's `OPENROUTER_API_KEY`,
     streaming text replies with no tools; a send to an Ur session without the
     key is refused with an error. Ur saves each prompt, and each reply as far

   run in the workspace without the API key, ask first in Manual, end after two
   minutes unless the model sets up to ten, and show at most the first and
   last 8 KiB of their output.
   - **Alternative:** no timeout. A command that never exits holds the turn
     until the user presses Stop, and an unattended child session hangs.

   in manual mode." to "...in manual and auto modes."
4. **Stopping oxd** changes from "Stopping `oxd` stops every Claude process it
   runs; a second stop request ends it at once." to "Stopping `oxd` stops every
   Claude process and Ur command it runs; a second stop request ends it at
   once."

## Test plan

New `internal/ur/shell_test.go`, calling `runShell` directly (Ur harness
layer; no existing test reaches the command runner):

- Output and status: `pwd; printf out; printf err >&2; read v` reports
  `Exit code: 0`, the workspace path, both streams, and a failed `read` from
  `/dev/null`; `exit 7` is an error with `Exit code: 7`; `kill -TERM $$`
  reports `Terminated by signal: 15`.
- `OPENROUTER_API_KEY` set in the test's environment is unset in the command.
- Output over 16 KiB keeps its first and last 8 KiB with the omitted count.
- Timeout: `timeout_seconds: 1` on `sleep 60 & echo $! > child; sleep 60`
  reports `Timed out after 1 seconds`, and the background child is gone.
- Cancellation: canceling the context mid-command returns promptly and the
  background child is gone.
- A command that exits leaving `sleep 60 &` holding the pipe returns within
  two seconds, and the child is gone.
- Argument checks: invalid JSON, missing `command`, an extra field,
  `timeout_seconds` 0, 601, and `"1"` each return an error outcome without
  running (`touch wrong` leaves no file).
