## F1. `isID`'s overflow check repeats what the round-trip does

Low · Simplicity · Fix · `internal/server/id.go:48`

`isID` uses `bits.Mul64` and `bits.Add64` to catch a value over 64 bits, then
checks that `encodeID(n)` gives back the string. The round-trip check already
rejects every overflowing string. A string's digits name exactly one number V.
When V is 2^64 or more, unchecked `uint64` arithmetic leaves V mod 2^64, which
is a different number. Its canonical encoding is therefore a different string.
No test can protect the overflow check, because nothing reaches it that the
round-trip would accept.

### Evidence

The overflow check was replaced with `n = n*58 + uint64(d)`.
`TestIDEncoding`, `TestSettingsValidation`, and `TestSessionLifecycle` still
pass, and `jpXCZedGfVR` is still refused. When `return encodeID(n) == id` was
replaced with `return true` instead, `TestIDEncoding` failed on `111111111`
and `TestSettingsValidation` failed on `12`. The original file was restored.

### Action

Replace the `Mul64`/`Add64` check with `n = n*58 + uint64(d)` and let the
round-trip reject overflow. Update `isID`'s comment, or add one beside the
loop, to say that wrapped arithmetic is caught by the round-trip. The plan's
Decision that "an overflow is false" still holds. `TestIDEncoding`'s
`jpXCZedGfVR` case already guards that rejection, so no new test is needed.
