## F1. Page budget, rune cut, and `invalid arguments` survive mutation

Low · Testing · Fix · Resolved · `internal/server/mcp_test.go:446`

Three conditions `readSession` adds have no test that fails without them:

- The budget counts runes (`utf8.RuneCountInString` in `transcriptPage`) and
  `cut` slices runes. Every filler in `TestReadSession` is ASCII, so counting
  and slicing bytes passes the test, although byte slicing splits a multi-byte
  rune and byte counting shortens pages of non-ASCII text.
- The separator's cost (`cost += len("\n\n")`). The paging case's entries are
  15,011 runes, so two fit and three do not whether or not separators count;
  removing the line passes.
- `arguments that do not decode → invalid arguments`. With the decode check
  removed, `{"to": 5}` falls through to `to is required`; no test sends
  undecodable arguments.

### Evidence

In a worktree copy of the change, each mutation was applied alone and
`go test -run 'TestReadSession|TestSendMessage|TestApprovalRouting'` run:
`cost := len(entry)`, `cost += 0`, and `return text[:n] + "…"` in `cut` all
pass. Every other condition the change adds fails a test when removed: the
`(failed)` mark, the queued count, both cursor bounds, the blank-`to` check,
the local time zone, and `ToolName` in both harnesses.

### Action

Extend `TestReadSession`'s long target, at the same server layer:

- Fill at least one paged entry and the oversized first entry with a
  multi-byte character (such as `é`), sized so rune counting and byte counting
  page differently, and assert the oversized entry is cut at 40,000 runes.
- Add a page whose fit turns on the separator: two entries whose rendered
  runes sum to 40,000 or less only without the 2-rune separator, and assert
  they land on separate pages.
- Add `{"to": 5}` (or any undecodable arguments) to the refusals, expecting
  `invalid arguments`; `TestReadSession` or `TestSendMessage`'s refusal table
  can carry it.

## F2. `claude-code.md` claims more than the live case observes

Low · Claude Code · Fix · Resolved · `docs/claude-code.md:41`

The new line says a ~38,000-character MCP tool result "reaches the model
whole, and the `tool_result` the stream reports carries all of it". The live
case in `TestLive` asserts only the second half: the stream's `tool_result`
contains the end marker and is at least 38,000 characters long. The reader is
asked to reply "ok", so nothing shows the model saw the end of the result.
The plan names this fact as the reason for the live case ("Not recorded: that
a tool result near 40,000 characters reaches the model whole"), and the page
size rests on it: a cut result would drop the newest entries and the state
line, the part a reader needs most.

### Evidence

`internal/server/live_test.go:179-198`: the reader's prompt is "Load and call
the mcp__ox__read_session tool with to set to <id>. Then reply with just ok.",
and the assertions read only `tool_result` updates.

### Action

Have the live reader observe the end of the page: ask it to reply with the
marker that ends the other session's first prompt, keep the existing
`tool_result` assertions, and assert the reader's `result` text contains
`endMarker`. The marker appears only in the target's transcript, so the reply
shows the model received the end of the result. Keep the `claude-code.md`
line as written once that passes; if Haiku cannot answer reliably, narrow the
line to what the stream shows instead.

## F3. Tool input is compacted twice, with a fallback that cannot run

Low · Simplicity · Fix · Resolved · `internal/server/mcp.go:380`

`renderEntry` runs `json.Compact` on a `tool_use` input and, if that fails,
writes the raw input instead. Every `tool_use` in `history.entries()` comes
from the store, written by `history.append` with `json.Marshal`, which
compacts a `json.RawMessage` (and fails on invalid JSON, so nothing invalid is
stored). The input is already compact and valid, so the `json.Compact` call
and its fallback add no behavior.

### Evidence

Replacing the condition with `if true {` (skipping `json.Compact` and writing
the raw input) passes `TestReadSession`, whose seeded `{ "a": 1 }` still
renders `{"a":1}`, because the seed itself goes through `json.Marshal` as
`history.append` does.

### Action

Render the input as stored: `cut(string(u.Input), toolInputRunes)`, and drop
the `bytes` import and the buffer. The existing `Tool: Read {"a":1}`
assertion keeps covering the one-line form, which the store's marshalling now
guarantees.
