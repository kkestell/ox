## F1. The viewer's text memos are redundant and the held scroll is untested

Low · Testing · Fix · `cmd/ox/web/src/FileView.tsx:14` · Resolved

The plan's Decision is that an unchanged file writes nothing to the DOM and
the pane's scroll position holds. `FileView` wraps `text` and `error` in
`createMemo` for this. The memos add nothing: Solid's insert already skips a
string identical to the one it shows, and `Show` compares its condition. With
the memos replaced by plain accessors, the text node and the scroll position
both survive polling. No kept test checks the behavior, which the implementer
also reported.

### Evidence

A temporary e2e probe opened a 400-line file with long lines, set the `<pre>`'s
`scrollTop` to 2000 and `scrollLeft` to 300, marked its text node, and waited
2.5 s (two or more polls). With the memos: `[2000, 300, 1]`. With both
`createMemo` calls replaced by plain functions: `[2000, 300, 1]`. The probe
was removed and the file restored.

### Action

Replace the two memos with plain accessors and drop their comment. In "the
file viewer shows each session's open file" in
`cmd/ox/web/e2e/workspace.spec.ts`, after the step that shows the pane scrolls
horizontally, make the file tall enough to scroll vertically too, set the
`<pre>`'s `scrollTop` and `scrollLeft`, wait past two ticks, and assert both
are unchanged. The test guards the plan's held scroll position whatever
mechanism keeps it.

## F2. `readFile` and `listFolder` handlers repeat their lookup

Low · Simplicity · Rejected · `internal/server/methods.go:271`

`Server.readFile` repeats `Server.listFolder`'s decoding, path check, and
workspace lookup line for line.

### Action

Rejected: the plan chose to mirror `listFolder`, the two differ on the empty
path (the root is a folder, not a file), and a shared helper would need a flag
for that difference. Two short handlers cost less than the helper.
