## F1. Configuration test configures the running session after its background task

Low · Testing · Fix · Resolved · `internal/server/methods_test.go:444`

`TestConfigurationTakenButNotStored` sends `background 2000` with this comment:
"The background task keeps the running session from parking until it has taken
its configuration". It then waits for the `idle` state. While a task runs, the
tracker publishes `background`, not `idle` (`tracker.go:30`). `idle` arrives
only when the task ends, and then `Parkable` becomes true and the 100 ms park
timer starts. The test closes the store and configures the running session
inside that 100 ms window. The background task does not protect the
configuration, so the comment is false.

If the session parks first, for example on a loaded machine, the "running" half
configures a parked session, and the test checks the parked path twice without
reporting it. The plan's mutation still fails the test, because both paths go
through `adopt`. What the test claims to cover depends on timing.

### Evidence

The test takes 2.17 s (`go test -run 'TestConfigurationTakenButNotStored$' -v`),
so `idle` arrives only after the 2000 ms task. The trace: `fake.begin` calls
`SetTasks(1)`, and `finish` reports idle, which `Tracker.State` publishes as
`background`. `taskEnded` then publishes `idle`. `fake.Parkable` requires
`Tasks() == 0`.

### Action

Wait for the running session's `background` state, not `idle`, before closing
the store. `fake.Configure` accepts a configuration while background work runs,
since `idle()` counts `background`. `Parkable` stays false until the task ends,
so the configuration reaches a live process every time, and
`c.update(id, agent.UpdateParked)` then waits for the park after the task. Keep
the comment, which becomes true. No new test.
